# 分布式追踪系统

## 1. 一句话定义

分布式追踪（Distributed Tracing）通过追踪一个请求在多个服务间的完整调用链路，帮助开发者理解分布式系统的行为、定位性能瓶颈和排查故障。

## 2. 核心问题

- 一个用户请求经过了哪些服务和中间件？
- 每段调用的耗时是多少？瓶颈在哪里？
- 如何在不显著影响性能的前提下收集追踪数据？

## 3. 知识框架

| 概念 | 说明 |
|------|------|
| Trace（追踪）| 一个请求的完整调用链路，由多个 Span 组成 |
| Span（跨度）| 一次独立的操作（如 RPC 调用、DB 查询），含起止时间 |
| Trace ID | 全局唯一标识一个 Trace，全链路传递 |
| Span ID + Parent Span ID | 标识 Span 的父子关系，构成调用树 |
| Context Propagation | 在服务间传递 Trace/Span 信息的机制 |

## 4. 关键概念

- **Dapper 论文（Google, 2010）**：分布式追踪的奠基之作——定义了 Trace、Span、Context Propagation 的核心框架
- **OpenTelemetry**：CNCF 的开放可观测性标准，统一 Trace + Metrics + Logs 的 API/SDK
- **采样（Sampling）**：并非所有请求都需要追踪——头部采样（入口决定）vs 尾部采样（根据延迟/错误决定）
- **上下文传播（Context Propagation）**：通过 HTTP Header（W3C TraceContext）或 gRPC Metadata 传递 trace-id 和 span-id
- **Jaeger / Zipkin**：两个最主流的开源分布式追踪系统

## 5. 典型机制

### 5.1 追踪数据流

```
应用（SDK 生成 Span）
    ↓
Collector（收集、缓冲）
    ↓
存储（Elasticsearch / ClickHouse / Cassandra）
    ↓
UI（Jaeger UI / Grafana）
```

### 5.2 Span 的基本字段

```
Span {
  trace_id: "abc123"
  span_id:  "span-2"
  parent_span_id: "span-1"
  operation_name: "GET /api/users"
  start_time: 1234567890
  duration: 42ms
  tags: {http.status_code: 200, db.type: "mysql"}
}
```

## 6. 经典问题

- 追踪数据量巨大——如何平衡采样率和信息完整性
- 异步消息队列中的追踪链路断裂
- 时序偏差——不同服务的时间不同步
- 高基数标签导致存储爆炸

## 7. 工程实践

- 用 Jaeger 或 Zipkin + Docker Compose 搭建本地追踪系统
- 在应用中集成 OpenTelemetry SDK 自动采集 HTTP/gRPC 调用
- 分析一个慢请求的 Trace 定位性能瓶颈
- 配置尾部采样保留错误和慢请求的 Trace

## 8. 与其他主题的关系

| 相关主题 | 关系 |
|----------|------|
| 微服务架构 | 分布式追踪是微服务可观测性的支柱 |
| 可观测性 | 与指标（Metrics）、日志（Logs）构成三支柱 |
| 容器/K8s | Sidecar 模式常用于部署追踪 Agent |
