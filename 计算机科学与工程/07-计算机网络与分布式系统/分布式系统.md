# 分布式系统

## 1. 一句话定义

分布式系统由多个通过网络连接的自治计算节点组成，协同工作以为用户呈现单一一致的系统。

## 2. 核心问题

- 如何在部分节点故障时保持系统可用？
- 如何让分布在多台机器上的数据保持一致？
- 如何在网络延迟和分区的情况下做出正确决策？

## 3. 知识框架

| 主题 | 核心问题 | 关键技术/协议 |
|------|----------|---------------|
| 共识 | 多节点如何就一个值达成一致？ | Raft、Paxos |
| 复制 | 如何保证多副本数据一致？ | 主从复制、多主、无主 |
| 分片 | 如何将数据分布到多个节点？ | 一致性哈希、范围分片 |
| 分布式事务 | 如何跨节点原子提交？ | 2PC、3PC、Saga |
| 一致性模型 | 系统提供什么样的数据一致性？ | 线性一致性、因果一致性、最终一致性 |
| 故障检测 | 如何快速发现节点失效？ | 心跳、Gossip 协议 |

## 4. 关键概念

- **CAP 定理**：分布式系统最多同时满足一致性（Consistency）、可用性（Availability）和分区容忍性（Partition Tolerance）中的两个——实际上分区容忍性不能牺牲，变为 CP vs AP 的选择
- **拜占庭将军问题**：在可能存在恶意节点的系统中达成共识——区块链的核心问题
- **线性一致性（Linearizability）**：最强的一致性模型——所有操作看起来在某个瞬间原子完成
- **最终一致性**：如果不再有新的写操作，所有副本最终会收敛到相同值——AP 系统的选择
- **Quorum 机制**：R + W > N（读写副本数之和大于总副本数）保证读写一致性

## 5. 典型机制

### 5.1 Raft 共识协议

```
角色：Leader / Follower / Candidate
任期（Term）：逻辑时钟，每个任期最多一个 Leader
正常流程：
  Leader 接收写请求 → 追加到本地日志 → 广播 AppendEntries
  → 多数派确认后提交 → 返回客户端
选举：Follower 超时未收到心跳 → 变为 Candidate，发起选举
```

### 5.2 一致性模型对比

| 模型 | 强度 | 典型系统 |
|------|------|----------|
| 线性一致性 | 最强 | etcd、ZooKeeper |
| 顺序一致性 | 强 | 少数数据库 |
| 因果一致性 | 中等 | MongoDB（因果一致会话）|
| 最终一致性 | 弱 | Cassandra、DynamoDB |

## 6. 经典问题

- 分布式事务与两阶段提交（2PC）的阻塞问题
- 网络分区（Split-Brain）导致的双主问题
- 时钟不可靠性与逻辑时钟（Lamport 时钟、向量时钟）
- 分布式锁的安全性和活性

## 7. 工程实践

- 使用 etcd 实现分布式配置管理和服务发现

- 设计幂等接口以处理重试和至少一次送达
- 理解分布式追踪（如 Jaeger）的原理和用法
