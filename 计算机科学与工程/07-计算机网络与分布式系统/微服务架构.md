# 微服务架构

## 1. 一句话定义

微服务架构将应用拆分为一组小型、独立部署、围绕业务能力组织的服务，每个服务拥有自己的数据并通过轻量级协议通信。

## 2. 核心问题

- 如何拆分单体应用为合适的服务粒度？
- 服务之间如何可靠通信和数据一致？
- 如何管理服务发现、配置和可观测性？

## 3. 知识框架

| 组件 | 核心功能 | 代表性技术 |
|------|----------|------------|
| 服务通信 | 同步 RPC/异步消息 | gRPC、REST、Kafka |
| 服务发现 | 动态注册与发现 | Consul、etcd、Eureka |
| API 网关 | 路由、认证、限流 | Kong、Envoy、Nginx |
| 配置管理 | 集中化配置与热更新 | ConfigMap、Apollo |
| 可观测性 | 日志、指标、追踪 | Prometheus、Jaeger、ELK |
| 服务网格 | 透明代理服务通信 | Istio、Linkerd |
| 数据管理 | 每个服务独立数据库 | Saga 模式、事件溯源 |

## 4. 关键概念

- **服务拆分原则**：按业务能力（DDD 限界上下文）、单一职责、独立部署
- **数据库按服务独立**：每个微服务拥有自己的数据库——避免共享数据库导致耦合
- **Saga 模式**：用本地事务 + 补偿操作实现最终一致性的分布式事务
- **断路器（Circuit Breaker）**：检测下游故障，快速失败而非等待超时
- **服务网格 Sidecar**：每个 Pod 旁挂代理，透明处理服务间通信的负载均衡、重试、加密

## 5. 典型机制

### 5.1 微服务技术栈

```
入口 → API 网关（路由、认证、限流）
           ↓
服务注册/发现（Consul/etcd）
           ↓
服务通信（gRPC/REST + 服务网格 Sidecar）
           ↓
数据层（每服务独享 DB）
           ↓
可观测性（Prometheus 指标 + Jaeger 追踪 + ELK 日志）
```

### 5.2 单体 vs 微服务

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 部署 | 整体部署 | 独立部署 |
| 扩展 | 整体扩展 | 按服务扩展 |
| 技术栈 | 统一 | 多语言 |
| 开发速度 | 初期快 | 长期快 |
| 运维复杂度 | 低 | 高 |
| 调试 | 简单 | 复杂 |

## 6. 经典问题

- 分布式事务——不能依赖单数据库的 ACID 事务
- 服务间通信的延迟叠加
- 数据一致性在微服务中的最终一致性实践
- 过多的微服务导致的"微服务地狱"

## 7. 工程实践

- 将一个简单单体应用拆分为 2-3 个微服务
- 使用 Docker Compose 或 K8s 进行微服务部署
- 集成 Prometheus + Grafana 监控微服务指标
- 实现 API 网关的认证和限流功能
