# 分布式锁的实现

## 1. 一句话定义

分布式锁在多个进程/节点之间协调对共享资源的互斥访问，是分布式系统中防止并发写入冲突的基础构件。

## 2. 核心问题

- 在部分节点可能故障的前提下，如何安全且高效地实现锁？
- 锁被持有时如何防止持有者宕机导致的死锁？
- 如何兼顾正确性、性能和易用性？

## 3. 知识框架

| 实现方案 | 核心机制 | 特点 |
|----------|----------|------|
| Redis 锁 | SET NX + 过期时间 | 高性能，但需要额外的安全措施 |
| ZooKeeper 锁 | 临时顺序节点 + Watch | 强一致，自动释放 |
| etcd 锁 | Lease + 事务 | 强一致，支持租约 |
| 数据库锁 | SELECT FOR UPDATE | 简单但性能有限 |

## 4. 关键概念

- **互斥性（Safety）**：同一时刻只有一个客户端持有锁——这是分布式锁的底线
- **无死锁（Liveness）**：锁最终会被释放——依赖过期时间（TTL）或临时节点自动清理
- **锁的续期（Lease/Renew）**：持有者在操作完成前持续续期——防止 TTL 过期导致锁被他人抢占
- **Redlock 算法**：Redis 作者提出的多节点分布式锁方案——向 N 个独立 Redis 实例获取锁，多数派成功则获得
- **Redlock 争议**：Martin Kleppmann 指出 Redlock 在时钟跳跃等场景下不安全——分布式锁的正确性远比看起来复杂

## 5. 典型机制

### 5.1 简单 Redis 分布式锁

```
加锁: SET lock_key random_value NX EX 30
      (NX=不存在时才设置, EX=过期30秒)
解锁: Lua 脚本检查 random_value → 匹配则删除
      (必须用 Lua 保证原子性，不能简化为 get+delete)

续期: 启动后台线程，每 N/3 秒检查 + 续期
```

### 5.2 etcd 分布式锁

```
1. 创建 Lease（租约，带 TTL）
2. 事务写入：if key 不存在 → 创建 key + 绑定 Lease
3. 启用心跳自动续租
4. 释放锁：删除 key 或撤销 Lease
5. 若客户端崩溃 → Lease 过期 → key 自动删除 → 锁释放
```

## 6. 经典问题

- 如何安全地实现锁的自动过期——续期 vs 无续期的权衡
- 时钟不同步对 TTL 的影响
- GC 导致的"假过期"——进程被 GC 暂停，锁已过期但进程以为自己仍持有锁
- Fencing Token——在存储端验证锁的持有者，防止过期后继续写入

## 7. 工程实践

- 用 Redis 实现简单分布式锁并处理续期和自动释放
- 在 etcd/ZooKeeper 上实现分布式锁并观察节点故障时的自动恢复
- 使用 Fencing Token 保护存储层的并发安全
- 对比不同实现方案在延迟、吞吐量和复杂度上的差异
