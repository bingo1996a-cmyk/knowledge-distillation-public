# 设计模式

## 1. 一句话定义

设计模式是针对反复出现的软件设计问题的通用解决方案，不是可直接复用的代码而是解决思路的模板——"在特定上下文中解决问题的命名方案"。

## 2. 核心问题

- 如何避免重复发明轮子——复用已被验证的设计经验？
- 如何编写易于扩展、易于修改的代码？
- 如何在设计层次表达意图——让代码结构本身传达架构思想？

## 3. 知识框架（GoF 23 模式分类）

| 类别 | 核心关注 | 代表性模式 |
|------|----------|------------|
| 创建型 | 对象创建的灵活性和控制 | 单例、工厂方法、建造者 |
| 结构型 | 类和对象的组合方式 | 适配器、装饰器、代理 |
| 行为型 | 对象之间的责任分配和协作 | 观察者、策略、模板方法 |

## 4. 关键概念

- **SOLID 原则**：单一职责（SRP）、开闭原则（OCP）、里氏替换（LSP）、接口隔离（ISP）、依赖反转（DIP）
- **组合优于继承**：运行时组合比编译时继承更灵活——Decorator 和 Strategy 模式的基石
- **依赖注入**：将依赖的创建交给外部容器，实现控制反转（IoC）
- **封装变化**：识别可能变化的方面，将其封装在独立的类中——大多数模式的核心思想

## 5. 典型模式

### 5.1 策略模式

```
意图：定义一系列算法，使其可以互相替换
结构：
  Context → 持有 Strategy 引用
  Strategy（接口）→ 声明算法接口
  ConcreteStrategyA/B → 实现具体算法
关键：将算法的选择和实现分离，运行时切换
```

### 5.2 核心模式速览

| 模式 | 解决什么问题 | 一句话描述 |
|------|-------------|------------|
| 工厂方法 | 延迟对象的创建 | 子类决定创建什么 |
| 适配器 | 接口不兼容 | 转换一个接口到另一个 |
| 装饰器 | 动态添加职责 | 包装对象增加功能 |
| 观察者 | 一对多依赖通知 | 订阅-发布 |
| 策略 | 算法族可互换 | 组合而非继承 |

## 6. 经典问题

- 模式滥用——为了用模式而用模式（Patternitis）
- 过度抽象导致代码理解困难
- 模式与实践的差距——书中示例 vs 真实生产代码
- 模式在不同语言中的表达差异——函数式语言对 GoF 模式的简化

## 7. 工程实践

- 在重构时识别可应用模式的机会而非预先设计
- 阅读 JDK 和 Spring 源码中的模式使用实例（IO 装饰器、Bean 工厂）
- 用模式名称在代码审查中快速传达设计意图
- 关注 SOLID 原则而非死记硬背模式

## 8. 与其他主题的关系

| 相关主题 | 关系 |
|----------|------|
| 软件架构 | 模式是架构风格的局部实现手段 |
| 需求工程 | 需求变化是驱动模式选择的关键因素 |
| 编程语言理论 | 语言的表达能力影响模式的必要性 |
