# 程序分析与验证

## 1. 一句话定义

程序分析在不运行程序的情况下推断程序的行为性质，形式验证用数学方法证明程序满足其规范——二者是构建高可信软件系统的核心技术。

## 2. 核心问题

- 如何在程序运行前发现潜在 Bug？
- 如何用数学方法证明关键代码的正确性？
- 如何在精度和效率间做出合理权衡？

## 3. 知识框架

| 方法 | 核心思想 | 代表性工具 |
|------|----------|------------|
| 静态分析 | 分析源码/字节码推断运行时信息 | SonarQube、ESLint |
| 符号执行 | 用符号值执行程序收集路径约束 | KLEE、SMT 求解器 |
| 抽象解释 | 在抽象域上近似程序语义 | Astrée（空客，A380 控制软件零运行时错误）|
| 模型检验 | 穷举搜索系统状态空间 | SPIN、TLA+ |
| 定理证明 | 机器辅助数学证明 | Coq、Lean、Isabelle |

## 4. 关键概念

- **Sound vs Complete**：Sound（不遗漏 Bug，可能有误报）vs Complete（所有报告都是真 Bug，可能漏报）——静态分析必须牺牲 Complete 换取可判定性
- **抽象解释（Abstract Interpretation）**：在抽象域上执行程序——如符号域（正/零/负）、区间域（[0,10]）——得到真实程序行为的近似
- **符号执行（Symbolic Execution）**：用符号值代替具体值执行，在每个分支点收集路径约束——用 SMT 求解器判断约束是否可满足
- **Hoare 三元组**：{P} C {Q}——若前置条件 P 成立，执行完程序 C 后后置条件 Q 成立——程序验证的逻辑基础
- **Curry-Howard 对应**：程序 = 证明，类型 = 命题——依赖类型语言（Coq/Lean）可作为定理证明器

## 5. 典型机制

### 5.1 静态分析 vs 动态分析

| 维度 | 静态分析 | 动态分析 |
|------|----------|----------|
| 何时 | 编译时/不运行 | 运行时 |
| 覆盖率 | 覆盖所有代码路径 | 只覆盖实际执行路径 |
| 误报 | 有 | 无 |
| 开销 | 编译期间 | 运行时额外开销 |
| 工具 | SonarQube、Coverity | Sanitizer、Valgrind |

### 5.2 工业级形式验证案例

| 系统 | 方法 | 效果 |
|------|------|------|
| A380 飞控软件 | 抽象解释（Astrée）| 证明无运行时错误 |
| seL4 微内核 | 定理证明（Isabelle/HOL）| 完全功能正确性证明 |
| Amazon S3/DynamoDB | 模型检验（TLA+）| 发现多个设计缺陷 |
| AWS 关键服务 | 模型检验（TLA+）| 避免分布式 Bug |

## 6. 经典问题

- 路径爆炸——符号执行在分支多时路径数指数增长
- 指针/别名分析——两个指针是否指向同一内存
- 跨过程分析的精度-开销权衡
- 形式验证的工程成本——"证明正确性"的人力成本极高

## 7. 工程实践

- 用 Coverage-Guided Fuzzing（如 AFL/libFuzzer）自动发现 Bug
- 用 TLA+ 验证分布式算法设计
- 在 CI 中集成静态分析工具（如 SonarQube、Semgrep）
- 理解 Rust 借用检查器作为类型级静态分析的范例
