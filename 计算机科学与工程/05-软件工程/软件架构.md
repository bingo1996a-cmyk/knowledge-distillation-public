# 软件架构

## 1. 一句话定义

软件架构是系统的骨架——定义主要组件、它们之间的关系以及指导设计和演化的关键决策，是功能需求和非功能需求之间的桥梁。

## 2. 核心问题

- 如何将系统分解为可理解、可独立演化的组件？
- 如何确保系统满足性能、可用性、安全性等质量属性？
- 架构决策如何在长期演化中保持有效？

## 3. 知识框架

| 维度 | 核心内容 | 关键概念 |
|------|----------|----------|
| 架构风格 | 高层组织模式 | 分层、微服务、事件驱动 |
| 质量属性 | 非功能性需求 | 性能、可用性、安全性、可维护性 |
| 架构视图 | 多视角描述架构 | 4+1 视图模型 |
| 架构决策 | 权衡与记录 | ADR（架构决策记录）|
| 评估方法 | 架构评审 | ATAM、轻量级评审 |

## 4. 关键概念

- **架构风格 vs 设计模式**：风格是系统级组织原则，模式是局部设计方案
- **质量属性（QA）**：性能、可扩展性、可用性、安全性、可维护性、可测试性——架构的核心关切
- **4+1 视图模型**：逻辑视图 + 过程视图 + 开发视图 + 物理视图 + 场景视图
- **架构决策记录（ADR）**：记录"做了什么决定、为什么、有哪些替代方案被拒绝"
- **康威定律**：系统架构会反映组织的沟通结构

## 5. 典型架构风格

| 风格 | 核心思想 | 适用场景 |
|------|----------|----------|
| 分层架构 | 逐层调用，单向依赖 | 企业应用 |
| 六边形架构 | 领域核心 + 端口/适配器 | DDD 应用 |
| 微服务 | 小型独立服务 + 轻量通信 | 大规模分布式系统 |
| 事件驱动 | 发布/订阅，异步解耦 | 实时处理系统 |
| CQRS | 命令查询职责分离 | 高并发读写系统 |
| 管道-过滤器 | 数据流经处理阶段 | 数据管道 |

## 6. 经典问题

- 过度设计（Over-Engineering）vs 设计不足——找到合适的复杂度
- 架构侵蚀（Architecture Erosion）——初始设计随迭代退化为大泥球
- 分布式单体——看似微服务但实质高度耦合
- 分析瘫痪（Analysis Paralysis）——在架构设计上花费过多时间

## 7. 工程实践

- 为项目绘制架构图（C4 模型：Context → Container → Component → Code）
- 写一份 ADR 记录一个架构决策
- 分析现有系统的质量属性优先级并验证架构是否匹配
- 使用 `arc42` 模板文档化软件架构

## 8. 与其他主题的关系

| 相关主题 | 关系 |
|----------|------|
| 设计模式 | 模式是架构在局部设计中的体现 |
| 需求工程 | 质量属性需求驱动架构决策 |
| 微服务架构 | 当前主流的分布式系统架构风格 |
| 数据库 | 数据存储决策是架构的核心部分之一 |
