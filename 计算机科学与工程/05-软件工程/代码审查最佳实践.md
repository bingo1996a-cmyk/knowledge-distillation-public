# 代码审查最佳实践

## 1. 一句话定义

代码审查（Code Review）是开发者在代码合并前互相检查变更的过程——不仅是找 Bug，更是知识传递、设计讨论和团队标准的建立。

## 2. 核心问题

- 如何让代码审查高效而非瓶颈？
- 审查者应该关注什么、不应该关注什么？
- 如何让代码审查成为建设性的而非找茬的流程？

## 3. 知识框架

| 维度 | 关注点 |
|------|--------|
| 正确性 | 是否实现了预期功能？边界情况是否处理？ |
| 设计 | 架构、抽象是否合理？是否符合现有模式？ |
| 可维护性 | 命名、结构、注释是否清晰？6 个月后能看懂吗？ |
| 安全性 | 是否存在常见安全漏洞（OWASP Top 10）？ |
| 测试 | 测试是否覆盖关键路径和边界情况？ |
| 性能 | 是否有明显的性能问题（N+1 查询、不必要的拷贝）？ |

## 4. 关键概念

- **PR（Pull Request）大小**：最佳实践是 < 400 行/次 —— 小于 200 行的小 PR 审查质量最高
- **审查速度**：理想是 24 小时内开始审查——超过 24 小时开始累积上下文切换成本
- **自动化先行**：自动能检查的（格式化、类型检查、Lint、测试）应前置，人审查的是机器查不出来的
- **What vs How**：审查关注"做了什么事"和"为什么这样做"而非代码风格（交给自动化）
- **建设性语气**：用"我怎么理解..."、"考虑一下..."而非"你应该..."、"这不对"

## 5. 典型实践

### 5.1 审查者 Checklist

```
[ ] 理解这个 PR 的目的和范围
[ ] 检查设计——这是解决问题的最简方式吗
[ ] 检查正确性——逻辑、边界、错误处理
[ ] 检查测试——是否测试了应该测试的
[ ] 检查安全——输入验证、认证、授权
[ ] 检查可观察性——日志、指标
[ ] 明确区分"必须改"和"建议改"
```

### 5.2 提交者 Checklist

```
[ ] PR 描述清楚——why + what + 相关上下文
[ ] PR 大小合理——如果太大先拆
[ ] 自审一遍——作者是最好的第一审查者
[ ] 所有自动化检查通过
[ ] 标注需要审查者特别关注的地方
```

## 6. 经典问题

- 审查瓶颈——审查者太忙导致 PR 堆积
- 过度挑剔——在主观风格偏好上争论浪费精力
- 橡皮章审查——走形式而不真正审查
- 太多轮次——PR 在审查循环中反复太久

## 7. 工程实践

- 为团队制定简短的代码审查规范
- 使用 GitHub/GitLab 的 CODEOWNERS 自动分配审查者
- 在 CI 中集成自动化检查减少人工审查负担
- 定期回顾审查流程的效率
