# 遗留系统现代化改造

## 1. 一句话定义

遗留系统现代化改造是在不完全重写的前提下，通过一系列渐进策略改进老旧代码库的可维护性、可扩展性和技术栈——"不扔掉能用的，但让它变得更好改"。

## 2. 核心问题

- 重写还是渐进改造？什么信号决定选择哪条路？
- 如何在不中断业务的情况下替换技术栈？
- 从哪里开始改造才能产生最大的投资回报？

## 3. 知识框架

| 策略 | 描述 | 风险 |
|------|------|------|
| 绞杀者模式（Strangler Fig）| 逐步用新系统替换旧功能 | 低 |
| 抽象分支（Branch by Abstraction）| 在抽象层后替换实现 | 低 |
| 特性切换（Feature Toggle）| 通过开关控制新旧实现 | 中 |
| 全量重写 | 从零开始重建 | 极高 |
| 直接重构 | 在现有代码上持续改进 | 低-中 |

## 4. 关键概念

- **绞杀者模式（Strangler Fig Pattern）**：藤蔓缠绕并逐渐替代宿主树——新功能走新系统，旧功能逐步迁移
- **防腐层（Anti-Corruption Layer）**：在新旧系统之间建立翻译层，防止旧系统的设计污染新系统
- **特性切换（Feature Toggle）**：部署新旧两套代码，通过配置切换——方便灰度验证和快速回滚
- **技术债量化**：用静态分析工具度量技术债（复杂度、重复率、测试覆盖率）——改造前先量化
- **数据迁移**：遗留改造中最复杂的部分——双写、CDC、逐步迁移

## 5. 典型策略

### 5.1 绞杀者模式实施步骤

```
1. 识别可独立的模块（通常是读操作优先）
2. 在新系统中实现该功能
3. 路由层将对应请求导向新系统
4. 验证正确性 → 移除旧系统代码
5. 重复，直到旧系统被完全替代
```

### 5.2 重写 vs 渐进改造

| 信号 | 倾向 |
|------|------|
| 团队完全理解现有系统的行为 | 渐进改造 |
| 现有系统技术上无法演进（语言/框架已废弃）| 渐进替换（绞杀者）|
| 业务规则完全无文档、无人理解 | 先建测试，再改造 |
| 系统小且边界清楚 | 可以考虑重写 |
| 系统大且正在服务客户 | 几乎永远不要全量重写 |

## 6. 经典问题

- 改造过程中新老系统的数据一致性
- 没有测试的代码如何安全重构——先加"特征测试"（Characterization Test）
- 组织的改造意愿和技术投入不足
- 改造与业务需求之间的优先级冲突

## 7. 工程实践

- 对遗留代码补充特征测试（Capture 当前行为，即使不一定正确）
- 识别系统中变化最频繁的"热点模块"，优先改造
- 使用静态分析工具生成技术债报告
- 在设计文档中记录现有系统的架构问题和改造路线图
