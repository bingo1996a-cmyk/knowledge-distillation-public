# 领域驱动设计

## 1. 一句话定义

领域驱动设计（Domain-Driven Design, DDD）将软件设计的核心放在业务领域模型上，通过统一语言（Ubiquitous Language）连接技术人员和业务专家，用限界上下文（Bounded Context）管理大型系统的复杂性。

## 2. 核心问题

- 复杂业务逻辑如何在代码中清晰表达？
- 大型系统如何被分解为相对独立的子系统？
- 技术人员和业务人员如何说同一种语言？

## 3. 知识框架

| 层次 | 核心内容 | 关键概念 |
|------|----------|----------|
| 战略设计 | 系统拆分与边界划分 | 限界上下文、上下文映射 |
| 战术设计 | 领域模型实现 | 实体、值对象、聚合、领域事件 |
| 统一语言 | 连接业务与技术的通用语言 | Ubiquitous Language |
| 架构模式 | 领域层的隔离方式 | 六边形架构、CQRS |

## 4. 关键概念

- **统一语言（Ubiquitous Language）**：团队在代码、文档和对话中统一使用的术语——"创建订单"在代码里就是 `Order.create()` 而非 `DataProcessor.init()`
- **限界上下文（Bounded Context）**：一个术语在不同上下文中有不同含义——"用户"在认证上下文是账号信息，在电商上下文是买家/卖家
- **实体（Entity）vs 值对象（Value Object）**：实体有唯一标识且可变（如用户），值对象无标识且不可变（如地址、金额）
- **聚合（Aggregate）**：一组关联的实体和值对象，通过聚合根（Aggregate Root）统一访问——保证业务规则的一致性边界
- **领域事件（Domain Event）**：领域中发生的事情，驱动跨聚合、跨上下文通信

## 5. 典型机制

### 5.1 六边形架构（端口-适配器）

```
        端口（Ports—接口）
       /                  \
外部世界（HTTP/DB/MQ）      领域核心（DDD 战术模式）
       \                  /
        适配器（Adapters）
```

- 领域层在中心，不依赖任何外部实现
- 所有外部交互通过端口（接口）和适配器（实现）连接

### 5.2 战术模式速览

| 模式 | 是什么 | 例子 |
|------|--------|------|
| Entity | 有 ID，可变，有生命周期 | Order(id, status) |
| Value Object | 无 ID，不可变，替换 | Money(amount, currency) |
| Aggregate | 业务一致性边界 | Order + OrderItem |
| Repository | 聚合的持久化抽象 | OrderRepository.save(order) |
| Domain Service | 不属于任何实体的业务逻辑 | PricingService |
| Domain Event | 已发生的事情 | OrderPlaced { orderId, ... } |

## 6. 经典问题

- DDD 的适用边界——不是所有项目都需要 DDD（CRUD 应用不需要）
- 聚合设计——聚合太大导致并发冲突，太小导致不变量分散
- 微服务与限界上下文的关系——理想情况下一个限界上下文对应一个微服务
- 战术模式在函数式语言中的表达

## 7. 工程实践

- 为现有业务系统识别限界上下文
- 在代码中明确区分 Entity、Value Object、Aggregate
- 用事件风暴（Event Storming）工作坊梳理业务流程
- 实现六边形架构——领域层零外部依赖
