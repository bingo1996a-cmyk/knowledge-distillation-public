# 文件系统详解

## 1. 一句话定义

文件系统在块设备之上构建文件和目录的持久化抽象，通过 inode、日志和缓存等机制管理数据布局和元数据，在性能和可靠性间寻找平衡。

## 2. 核心问题

- 文件如何在磁盘上被组织和定位？
- 系统崩溃后如何保证文件系统的一致性？
- 如何通过缓存和预读提升文件访问性能？

## 3. 知识框架

| 层次 | 核心内容 | 关键概念 |
|------|----------|----------|
| VFS（虚拟文件系统）| 统一的文件操作接口 | `struct file_operations`、`struct inode_operations` |
| 物理布局 | 数据块、inode 表、超级块 | 块组、位图 |
| 元数据管理 | 文件名→inode 的映射 | 目录项（dentry）|
| 日志（Journaling）| 崩溃一致性保证 | Write-Ahead Log、Redo/Undo |
| 页面缓存（Page Cache）| 内存中的文件数据缓存 | 写回（Writeback）、预读 |

## 4. 关键概念

- **inode**：文件的身份证——存储文件大小、权限、时间戳、数据块指针，但不存储文件名（文件名在目录的 dentry 中）
- **间接块**：inode 有一个指向数据块的指针数组——直接块（小文件，12 个 4KB=48KB）→ 一级间接 → 二级间接 → 三级间接（支持大文件）
- **日志（Journal）**：在修改文件系统结构前先将操作记录写入日志区——崩溃恢复时重放日志保证一致性。三种模式：journal（数据+元数据）、ordered（元数据日志，数据先写，默认）、writeback（仅元数据日志）
- **页面缓存（Page Cache）**：内核使用空闲内存缓存文件数据——读先查缓存，写延迟刷盘
- **写时复制（COW）**：修改数据时写到新位置而非原地覆盖——btrfs 和 ZFS 的核心思想，天然支持快照

## 5. 典型机制

### 5.1 Ext4 文件布局

```
磁盘组织：
| Superblock | 块组描述符 | 块位图 | inode 位图 | inode 表 | 数据块 |

一个文件从创建到读取：
1. 创建：分配 inode → 更新 inode 位图 → 创建 dentry（目录项）
2. 写入：分配数据块 → 更新 inode 的数据块指针 → 标记脏页
3. 读取：dentry → inode → 根据偏移量找对应的数据块 → 返回数据
```

### 5.2 主流文件系统对比

| 文件系统 | 特点 | 适用 |
|----------|------|------|
| Ext4 | 成熟稳定，extent 代替间接块 | 通用 Linux 默认 |
| XFS | 分配组并行，大规模扩展 | 大文件、高并发 |
| btrfs | COW、快照、校验和、子卷 | 高级功能需求 |
| ZFS | COW、池化存储、数据完整性 | 数据可靠性优先 |
| F2FS | 面向闪存设计 | SSD 移动设备 |

## 6. 经典问题

- fsync 的语义和性能——返回时数据已持久化，但不能过于频繁
- 孤儿 inode——文件已删除但仍有进程打开它
- 碎片化——文件的物理块不连续降低顺序读速度
- 日志的写放大——同一个数据先写 Journal 再写数据区

## 7. 工程实践

- 使用 `df -i` 检查 inode 使用率（不是磁盘空间满而是 inode 耗尽的故障模式）
- 用 `strace` 追踪应用的文件系统调用序列
- 对比不同文件系统在相同工作负载下的性能（fio 基准测试）
- 理解 `O_DIRECT`（绕过页缓存）和 `O_SYNC`（同步写）的使用场景
