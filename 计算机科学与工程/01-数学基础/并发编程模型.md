# 并发编程模型

## 1. 一句话定义

并发编程模型（Concurrency Models）提供组织和管理多个同时进行的计算任务的抽象方式，不同的模型以不同的复杂度/性能/正确性权衡解决竞态条件、死锁和通信问题。

## 2. 核心问题

- 多个任务如何安全地共享数据？
- 任务之间如何通信和同步？
- 如何在正确性和性能之间找到合适的抽象层次？

## 3. 知识框架

| 模型 | 通信方式 | 同步机制 | 代表语言/框架 |
|------|----------|----------|---------------|
| 共享内存 + 锁 | 共享变量 | 互斥锁、条件变量 | C/Pthreads、Java |
| 消息传递 | Channel/Queue | 消息发送/接收 | Go（goroutine）、Erlang |
| Actor 模型 | 异步消息 | 邮箱 + 消息处理 | Erlang/Elixir、Akka |
| 异步编程 | Future/Promise | async/await | Rust、JavaScript、Python |
| STM（软件事务内存）| 共享变量 + 事务 | 乐观并发 | Clojure、Haskell |
| CSP（通信顺序进程）| Channel | 同步通信 | Go、Occam |

## 4. 关键概念

- **竞态条件（Race Condition）**：程序行为依赖线程的相对执行顺序——并发 Bug 的主要来源，难以复现和调试
- **死锁（Deadlock）**：多个线程相互等待对方持有的资源——四个必要条件：互斥、持有并等待、不可抢占、循环等待
- **Actor 模型**：一切皆 Actor——每个 Actor 有独立状态、邮箱，通过异步消息通信——天然无共享，Erlang 的基石
- **async/await**：协作式多任务——在 await 点交出控制权——比线程更轻量，适合 IO 密集型
- **CSP（通信顺序进程）**：通过 Channel 进行同步通信——"不要通过共享内存来通信，而是通过通信来共享内存"——Go 的哲学

## 5. 典型模型

### 5.1 并发模型对比

| 维度 | 共享内存+锁 | Actor | async/await | CSP |
|------|------------|-------|-------------|-----|
| 通信 | 共享变量 | 消息 | 共享/Future | Channel |
| 同步 | 锁 | 隐式 | await | 阻塞收发 |
| 正确性 | 难保证 | 较易 | 中等 | 较易 |
| 性能 | 高 | 中 | 高（IO）| 中 |
| 学习成本 | 中 | 低 | 中 | 低 |

### 5.2 选择指南

```
CPU 密集型并行：共享内存 + 线程池（需小心锁）
IO 密集型并发：async/await
分布式系统：Actor 模型（Erlang/Elixir）
混合场景：CSP（Go）——简单、组合性好
高可靠性要求：Actor + 崩溃恢复（Erlang 的 OTP）
```

## 6. 经典问题

- 锁的粒度——太粗（性能差）vs 太细（逻辑复杂、易出错）
- Actor 信箱溢出——生产者快于消费者的背压处理
- async 的"染色"问题——调用异步函数的函数也必须是异步的
- Goroutine 泄漏——启动 goroutine 后忘记等待其完成

## 7. 工程实践

- 用 Go 的 goroutine + channel 解决生产者-消费者问题
- 用 Rust 的 tokio 构建高性能异步网络服务
- 用 Erlang/Elixir 构建容错并发系统
- 理解 Rust 的 Send + Sync trait 如何静态防止数据竞争
