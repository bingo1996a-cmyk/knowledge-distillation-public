# 混沌工程

## 1. 一句话定义

混沌工程（Chaos Engineering）通过在生产环境中进行受控实验——主动注入故障——来验证系统在真实故障下的行为，将"我们的系统容错"从假设变为经过验证的事实。

## 2. 核心问题

- 真正发生故障时，系统的行为是否与设计一致？
- 冗余和降级机制真的有效吗？上次验证是什么时候？
- 如何在可控风险下进行故障演练？

## 3. 知识框架

| 主题 | 核心内容 |
|------|----------|
| 基本原则 | 假设驱动、受控爆炸半径、自动化实验 |
| 实验设计 | 稳态假设→故障注入→观察偏差→改进 |
| 故障注入 | 网络、资源、依赖、状态故障 |
| 平台与工具 | Chaos Mesh、Litmus、Gremlin |
| 组织实践 | Game Day、混沌实验文化 |

## 4. 关键概念

- **混沌工程 ≠ 随机搞破坏**：是系统化的实验——先定义稳态（正常指标），注入故障后观察是否有意外偏差
- **爆炸半径（Blast Radius）**：混沌实验的影响范围——从小范围开始（Canary 部署的单个实例），逐步扩大
- **Game Day（故障演练日）**：团队定期模拟大规模故障场景——检验 Runbook、提升响应能力
- **暗启动（Dark Launch）**：混沌实验在生产环境中默默运行，不影响用户——依赖流量复制或特性切换

## 5. 典型实验

### 5.1 常用故障注入类型

| 类别 | 实验 | 工具 |
|------|------|------|
| 网络 | 延迟注入、丢包、DNS 故障 | Chaos Mesh、iptables |
| 计算 | CPU 压力、内存耗尽、进程终止 | stress-ng、kill -9 |
| 依赖 | 下游服务超时/不可用 | Toxiproxy |
| 存储 | 磁盘满、IO 延迟 | dd、fio |
| 时钟 | 时钟偏移 | libfaketime |

### 5.2 混沌实验流程

```
1. 定义稳态假设：错误率 < 0.1%，延迟 P99 < 500ms
2. 设计实验：杀死 50% 的 Pod 会怎样？
3. 限制爆炸半径：只针对一个可用区的一个服务
4. 执行实验并实时监控指标
5. 发现偏差 → 修复弱点 → 验证 → 扩大范围
   无偏差   → 增加信心 → 扩大范围
```

## 6. 经典问题

- 混沌实验的自动化程度——从手动到持续自动化
- 混沌工程在非云原生环境中的应用限制

## 7. 工程实践

- 在 K8s 集群中安装 Chaos Mesh 并执行简单的 Pod Kill 实验
- 设计一个 Game Day：模拟数据库主库故障的完整场景
- 在非生产环境先验证混沌实验的安全性
- 为关键服务建立混沌实验的 CI 流水线（持续验证弹性假设）
