# 性能优化方法论

## 1. 一句话定义

性能优化不仅是应用具体技巧，更是一套系统化的方法论——先测量找瓶颈，再假设验证，最后代码改造——避免凭直觉优化。

## 2. 核心问题

- 如何系统化地找到真正的性能瓶颈？
- 如何确保优化是有效的而不仅仅是看起来有效？
- 不同层次（CPU/内存/IO/网络）的优化手段有哪些？

## 3. 优化框架

### 3.1 黄金三步法

```
1. 测量（Measure）：不要猜。用 profiling 工具找最热的函数和路径
2. 分析（Analyze）：为什么这里慢？CPU/内存/IO/锁/网络？
3. 优化（Optimize）：改造代码 → 回到步骤 1 验证
```

### 3.2 阿姆达尔定律的启示

```
加速比 = 1 / ((1-P) + P/S)
P: 可优化部分占比, S: 该部分的加速比

→ 优化非瓶颈部分收益递减
→ 先找占比最大的瓶颈优化
```

## 4. 关键概念

- **瓶颈（Bottleneck）**：限制系统整体吞吐量或延迟的最慢环节——优化任何非瓶颈部分都不会提升整体性能
- **基准测试（Benchmarking）**：受控条件下可重复测量——警惕：预热、JIT、死代码消除、缓存效应都影响结果的可信度
- **90/10 法则**：90% 的时间花在 10% 的代码上——找到并优化那 10%
- **过早优化**："We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil." — Donald Knuth

## 5. 典型方法

### 5.1 分层次优化策略

| 层次 | 典型瓶颈 | 工具 | 优化手段 |
|------|----------|------|----------|
| 算法 | O(n²)→O(n log n) | 复杂度分析 | 换算法/数据结构 |
| CPU | 分支预测失败、缓存 Miss | perf、火焰图 | 改内存布局、预取 |
| 内存 | 分配频繁、GC 停顿 | heaptrack、valgrind | 对象池、栈分配 |
| IO | 同步阻塞、小数据多次读写 | iostat、strace | 异步、批处理、缓冲 |
| 网络 | 连接数、TCP 开销 | tcpdump、ss | 连接池、零拷贝 |
| 锁 | 锁竞争、上下文切换 | perf lock | 缩小临界区、无锁 |

### 5.2 常用 Profiling 工具速查

| 场景 | 工具 |
|------|------|
| CPU 热点 | `perf record` + 火焰图、`pprof`（Go）|
| 内存分配 | `heaptrack`、`jemalloc` profiling |
| 锁竞争 | `perf lock`、`Mutex` 竞争统计 |
| IO 等待 | `iostat`、`iotop`、`blktrace` |
| 系统调用 | `strace -c`、`perf trace` |
| 网络延迟 | `tcpdump` + Wireshark、`ping`/`mtr` |

## 6. 经典问题

- 测量引入偏差（观测者效应）——profiling 本身消耗资源
- 过早优化——牺牲可维护性换取未经证实的性能改善
- 基准测试不可信——测试数据不代表真实负载
- 性能与可读性的权衡——不是每段代码都需要极致优化

## 7. 工程实践

- 对现有服务使用 `perf record` + 火焰图找 CPU 热点
- 用 `wrk`/`k6` 进行 HTTP 服务压力测试
- 在 CI 中集成性能回归测试（基准测试自动化）
- 为关键路径编写性能单元测试，防止优化被后续改动破坏

## 8. 与其他主题的关系

| 相关主题 | 关系 |
|----------|------|
| 体系结构 | 理解 CPU 缓存和流水线才能做 CPU 优化 |
| 操作系统 | IO/网络优化依赖 OS 知识 |
| 算法 | 算法选择是最根本的性能决策 |
