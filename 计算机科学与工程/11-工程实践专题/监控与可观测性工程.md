# 监控与可观测性工程

## 1. 一句话定义

监控告诉你系统是否在工作，可观测性让你能问"为什么它不工作"——通过指标（Metrics）、日志（Logs）和追踪（Traces）三个支柱，建立对系统内部状态的主动洞察能力。

## 2. 核心问题

- 如何在系统出问题之前发现问题？
- 当故障发生时，如何快速定位根因？
- 如何在大量信号中区分噪声和真正的异常？

## 3. 知识框架

| 支柱 | 回答什么问题 | 典型工具 |
|------|-------------|----------|
| Metrics（指标）| 系统是否正常？有多快？| Prometheus、VictoriaMetrics |
| Logs（日志）| 发生了什么具体事件？| Loki、ELK（Elasticsearch）|
| Traces（追踪）| 一个请求经过了哪些服务？| Jaeger、Tempo |
| Alerts（告警）| 什么时候需要人介入？| AlertManager、Grafana |
| Dashboards（仪表盘）| 系统状态一览 | Grafana |

## 4. 关键概念

- **可观测性三支柱**：Metrics（聚合数值，时序存储）、Logs（结构化事件，全文检索）、Traces（请求链路，DAG 树结构）
- **RED 方法（服务监控）**：Rate（请求速率）、Errors（错误率）、Duration（延迟）——微服务的三项核心指标
- **USE 方法（资源监控）**：Utilization（利用率）、Saturation（饱和度）、Errors（错误）——CPU、内存、磁盘、网络的监控框架
- **SLI/SLO/SLA**：服务等级指标 → 目标 → 协议——“99% 的请求在 300ms 内返回”的工程化表达
- **告警原则**：告警必须有可操作的动作 + 减少告警疲劳 + 区分页面级（紧急）和工单级（处理）

## 5. 典型实践

### 5.1 可观测性技术栈

```
应用层：
  OpenTelemetry SDK（自动采集 Metric/Trace/Log）

收集层：
  Prometheus（Metric 存储+查询）
  Grafana Loki（Log 存储+查询）
  Jaeger/Tempo（Trace 存储+查询）

可视化层：
  Grafana（统一仪表盘+告警）

告警层：
  AlertManager（告警路由、静默、分组）
  → PagerDuty/Slack/飞书
```

### 5.2 告警设计反模式

| 反模式 | 问题 | 改进 |
|--------|------|------|
| 对一切设告警 | 告警疲劳 | 只对 SLO 偏离设告警 |
| 告警无文档 | 响应者不知道怎么办 | 每条告警附 Runbook |
| 阈值固定 | 随时间不适用 | 基于异常检测或动态阈值 |
| 页面级全用 | 干扰休息 | 区分紧急和非紧急 |

## 6. 经典问题

- 基数爆炸——高基数标签导致 Prometheus 内存膨胀
- 告警洪水——一个根因触发数十条关联告警
- 可观测性成本——高频采样和大规模日志的存储费用
- 从被动响应到主动预测

## 7. 工程实践

- 用 Prometheus + Grafana 搭建应用的 RED 监控仪表盘
- 使用 OpenTelemetry SDK 集成自动采集
- 为关键 API 定义 SLO 并建立告警规则
- 在 Grafana 中关联 Metric → Log → Trace
