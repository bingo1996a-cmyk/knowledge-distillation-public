# 时序数据库

## 1. 一句话定义

时序数据库（Time-Series Database, TSDB）专门优化时间戳数据的写入、存储和查询，是监控系统、IoT 和金融数据处理的基础设施。

## 2. 核心问题

- 时序数据的写入和查询模式与通用数据库有什么不同？
- 如何高效压缩和降采样海量的时间序列数据？
- 如何支持高基数的时间序列（数百万个不同标签组合）？

## 3. 知识框架

| 主题 | 核心内容 |
|------|----------|
| 数据模型 | 时间戳 + 指标名 + 标签集 + 数值 |
| 写入优化 | 追加写、时间排序、批量提交 |
| 存储引擎 | 列式存储、时间分区、压缩 |
| 查询模式 | 时间范围查询、聚合、降采样 |
| 数据保留 | 自动过期（TTL）、降采样（Rollup）|

## 4. 关键概念

- **写多读少**：时序数据库通常面临海量写入（每秒百万级数据点），查询集中在聚合和最近数据
- **追加写为主**：数据按时间顺序到达，几乎不涉及更新和删除——简化了并发控制
- **时间分区**：按时间范围（小时/天）划分数据文件——便于过期删除和范围查询
- **降采样（Downsampling）**：将原始高精度数据按时间窗口聚合为粗粒度数据——节省存储
- **高基数问题**：标签组合过多导致索引膨胀——InfluxDB 和 Prometheus 的不同应对策略

## 5. 典型机制

### 5.1 TSDB vs 通用数据库

| 维度 | 通用数据库（MySQL/PG）| 时序数据库（InfluxDB/TimescaleDB）|
|------|----------------------|----------------------------------|
| 写入性能 | 一般 | 极高（追加写优化）|
| 时间范围查询 | 需索引优化 | 原生支持 |
| 数据压缩 | 一般 | 极高（10-100×）|
| 自动过期 | 需手动 | 内置 TTL |
| 聚合函数 | 基本 SQL 聚合 | 丰富的时序聚合（窗口、差值、变化率）|

### 5.2 主流 TSDB

| 系统 | 特点 | 适用 |
|------|------|------|
| InfluxDB | 独立 TSDB，类 SQL 查询 | 通用 IoT/监控 |
| Prometheus | 拉模型，专为 K8s 设计 | 云原生监控 |
| TimescaleDB | PostgreSQL 扩展 | 需要 ACID 的场景 |
| VictoriaMetrics | 高性能 Prometheus 兼容 | 大规模监控 |

## 6. 经典问题

- 高基数（High Cardinality）——标签值组合爆炸导致内存和索引膨胀
- 存储和查询的精度权衡——保留原始数据 vs 降采样
- 时间乱序写入的处理
- 数据空洞（缺失时间段）的填充策略

## 7. 工程实践

- 用 Prometheus + Grafana 监控应用和基础设施指标
- 用 InfluxDB 存储 IoT 传感器数据并可视化
- 实现数据的自动降采样和过期策略
- 分析高基数场景下不同 TSDB 的内存消耗

## 8. 与其他主题的关系

| 相关主题 | 关系 |
|----------|------|
| 数据仓库 | TSDB 用于监控指标，数仓用于业务分析 |
| OLAP/列存 | TSDB 本质上是面向时间维度的列式存储 |
| 可观测性 | Prometheus 是云原生监控的事实标准 |
