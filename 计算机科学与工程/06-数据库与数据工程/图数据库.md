# 图数据库

## 1. 一句话定义

图数据库以节点（Node）和边（Relationship）为基本数据单元，天然地存储和查询实体之间的连接关系，适合社交网络、推荐系统、欺诈检测等关系密集型场景。

## 2. 核心问题

- 为什么关系数据库在深度连接查询上性能差？
- 图数据库的存储和查询有什么独特优势？
- 何时应该用图数据库而非关系数据库？

## 3. 知识框架

| 主题 | 核心内容 |
|------|----------|
| 图数据模型 | 属性图模型（节点属性 + 边类型属性）|
| 图查询语言 | Cypher（Neo4j）、Gremlin（Apache TinkerPop）、SPARQL（RDF）|
| 图存储 | 邻接表无索引、邻接矩阵 |
| 图算法 | 最短路径、PageRank、社区发现、相似度 |
| 图数据库 vs 图计算引擎 | OLTP（Neo4j）vs OLAP（Spark GraphX）|

## 4. 关键概念

- **属性图模型**：节点（Node）有标签和属性键值对，边（Relationship）有类型、方向和属性——Neo4j 的核心模型
- **无索引邻接**：每个节点直接存储其邻接边的物理指针——深度遍历时无需索引查找，性能与图大小无关（仅与遍历深度有关）
- **Cypher 查询语言**：声明式图查询语言——`MATCH (a)-[:KNOWS]->(b) WHERE ... RETURN ...` 的 ASCII-art 风格
- **图数据库 vs 关系数据库 JOIN**：关系数据库通过外键 JOIN 模拟关系，多层 JOIN 导致性能指数退化；图数据库原生存储关系，每次跳转 O(1)

## 5. 典型机制

### 5.1 关系数据库 vs 图数据库的多跳查询

```
查询：找到"我"的朋友的朋友的朋友

关系数据库（3 次 JOIN）：
  SELECT ... FROM users u
  JOIN friendships f1 ON u.id = f1.user_id
  JOIN friendships f2 ON f1.friend_id = f2.user_id
  JOIN friendships f3 ON f2.friend_id = f3.user_id
  WHERE u.name = 'me'
  → 随着跳数增加 JOIN 开销指数增长

图数据库（3 次遍历）：
  MATCH (me)-[:FRIEND*3]->(fofof)
  WHERE me.name = 'me'
  → 每次遍历 O(1)，跳数增加开销线性增长
```

### 5.2 主流图数据库

| 数据库 | 模型 | 特点 |
|--------|------|------|
| Neo4j | 属性图 | 最成熟，Cypher 查询，ACID |
| ArangoDB | 多模型 | 文档+图+KV |
| JanusGraph | 属性图 | 分布式，可扩展 |
| Dgraph | 属性图 | 原生 GraphQL，分布式 |
| Amazon Neptune | 属性图+RDF | 托管服务 |

## 6. 经典问题

- 超级节点——拥有海量连接的节点导致遍历性能下降
- 图分区——分布式图存储的数据分区策略
- 图查询优化——与关系查询优化完全不同的挑战

## 7. 工程实践

- 用 Neo4j 构建社交关系图并进行社区发现
- 将传统 SQL 的多表 JOIN 改写为 Cypher 图查询
- 用图的中心性算法（PageRank、Betweenness）分析节点重要性
- 实现基于图的推荐（协同过滤 → 路径推荐）
