# TEVV 与保证案例 (Test, Evaluation, Verification and Validation, and Assurance Case for Control Systems)

## 定位

TEVV（测试、评估、验证与确认）在控制工程中处于**全生命周期质量保证的顶层**——它不是某个特定测试环节，而是从需求定义到退役的全过程中确保控制系统满足其功能性、可靠性、安全性和合规性要求的结构化活动集合。

保证案例（Assurance Case）则是将 TEVV 活动的证据组织成结构化论证的方法论。如果说 TEVV 活动是"产生证据的过程"，那么保证案例就是"用证据证明系统安全可信的论证"。在航空（DO-178C）、汽车（ISO 26262）、工业（IEC 61508）和医疗（IEC 62304）等安全关键领域，保证案例已成为认证的必要组成部分。

## 核心问题

**"如何证明系统是安全的？"**：安全问题本质上是一个不可穷举的问题——你不可能测试所有可能的输入组合、所有可能的故障模式和所有可能的运行条件。因此，安全论证必须将有限的测试证据与结构化的逻辑推理结合起来，形成一个令人信服的论证链。保证案例正是提供这种论证框架的方法论。

**"测试覆盖不完备性如何弥补？"**：即使达到 100% 的语句覆盖、分支覆盖和 MC/DC 覆盖，测试仍然无法证明控制算法在所有可能的运行场景下都是正确的（不可判定性）。弥补测试覆盖不完备性的方法包括：形式化验证（model checking、定理证明）、运行时监测（runtime monitoring）和冗余设计（diverse design）。

**"不确定性如何在保证案例中量化？"**：系统的不确定性来自传感器噪声、模型误差、制造公差、环境变化和操作者行为差异。保证案例需要对这些不确定性进行显式建模和量化，以论证在最坏情况下系统的安全性仍能被保证。

## 基本模型

**V 模型与 TEVV 的映射**：V 模型将系统开发过程映射为左侧的"自上而下分解"和右侧的"自下而上验证"。具体映射为：用户需求 -> 用户验收测试；系统需求 -> 系统验证测试；架构设计 -> 集成测试；详细设计 -> 单元测试；实现 -> 代码审查。每层验证活动的严格性随安全等级递增。

**GSN (Goal Structuring Notation)**：保证案例的标准建模语言，基本要素包括：
- Goal（G）：要求证的命题，如"系统在所有可预见的操作条件下都是安全的"
- Strategy（S）：论证策略，描述如何将顶层目标分解为子目标，如"通过分析所有已识别的危险来论证安全性"
- Evidence（E）：支撑子目标的具体证据，如"HIL 测试报告 #1024"、"FMEA 分析报告"
- Context（C）：论证的上下文信息，如"定义的操作条件范围为温度 -20 到 60 度"
- Assumption（A）：论证所依赖的假设，如"假设维护人员每 6 个月执行一次预防维护"
- Justification（J）：对策略选择合理的解释

GSN 的核心优势是强制要求显式记录假设——这些假设往往是安全论证链条中最薄弱但最容易被忽略的环节。

## 关键概念

**Verification vs Validation**：Verification（验证）回答"是否正确地构建了系统"——检查实现是否符合规格。Validation（确认）回答"是否构建了正确的系统"——检查系统是否满足用户真实需求。经典比喻：Verification 是检查你已经按照食谱正确地烘焙了蛋糕，Validation 是品尝后确认蛋糕确实好吃。

**覆盖度指标**：
- 语句覆盖（Statement Coverage）：每条语句至少执行一次。最低要求。
- 分支覆盖（Branch Coverage）：每个条件分支（if/else 的真假分支）至少执行一次。比语句覆盖严格约 1.3-1.5 倍。
- MC/DC 覆盖（Modified Condition/Decision Coverage）：每个条件的真值和假值都必须独立影响决策结果的至少一次。最严格的覆盖标准，复杂度为 $O(n)$ 而非 $O(2^n)$，是航空 DO-178C Level A 的强制性要求。

**DO-178C / ISO 26262 / IEC 61508 等级对应**：三者的安全完整性等级在概念上对应——DO-178C Level A 对应 ASIL D（汽车）和 SIL 3/4（工业），Level B 对应 ASIL C 和 SIL 2，Level C 对应 ASIL B 和 SIL 1，Level D 对应 ASIL A。等级越高，对 TEVV 活动（测试覆盖、文档完整性、工具认证）的要求越严格。

**独立验证与确认 (IV&V)**：由独立于开发团队的组织执行的 V&V 活动。IV&V 的核心价值在于独立视角——开发团队的认知锚定（design fixation）会使其忽略设计中的系统性缺陷。NASA 的经验数据表明，IV&V 可以发现 15%-25% 的额外缺陷，这些缺陷通常在开发团队的自测试中被遗漏。IV&V 通常增加 5%-15% 的项目总成本，但每投入 1 美元可避免 10-20 美元的在轨故障损失。

**Safety Case vs Security Case**：Safety Case 论证系统不会因随机故障或系统性问题导致不可接受的伤害。Security Case 论证系统不会因恶意攻击导致机密性、完整性和可用性受损。两者的方法论（GSN/CAE）和工具链高度相似，但分析的威胁模型不同——Safety 面向随机故障和系统性问题，Security 面向蓄意的对抗性攻击。

## 工程判断

**TEVV 资源分配**：安全关键系统的 TEVV 活动通常消耗项目总预算的 40%-50%。典型的分配比例：需求验证（10%）、架构评审（5%）、单元测试（15%）、集成测试（15%）、系统级测试（15%）、HIL 测试（20%）、IV&V（15%）、认证文档编制（5%）。这个比例因系统的安全等级和目标行业标准而异——ASIL D 的汽车系统 TEVV 预算通常更高。

**举证负担递减原则**：举证负担递减原则指的是——先做最高"举证效率"的活动来覆盖尽可能多的风险，再用精确定向测试覆盖剩余风险。具体实施路径：（1）先做形式化分析和静态分析（一次扫描覆盖所有代码路径）；（2）然后做 MC/DC 覆盖测试（覆盖所有条件-决策关系）；（3）再做基于需求的定向测试（覆盖需求中每个功能点）；（4）最后做随机/边界测试（寻找未覆盖的非预期行为）。这一原则确保在有限的 TEVV 预算下最大化覆盖范围。

**工具认证的分级策略**：安全关键系统中的开发和验证工具也需要经过认证。工具认证分为三个等级——TCL 1（工具输出不直接影响可执行代码，低风险，如代码格式检查工具，无需认证）、TCL 2（工具输出参与代码生成但可被独立验证，如编译器，需工具的资格认证）、TCL 3（工具输出直接嵌入最终系统且不可被独立验证，如自动化代码生成器，需最高级别的认证）。设计师应优先使用 TCL 1/2 的成熟工具链，将 TCL 3 工具的使用限制在经严格验证的范围内。

## 常见误区

**误区一："测试覆盖率越高，系统就越安全"**。这是 TEVV 中最常见也最危险的误解。测试覆盖率（MC/DC、分支覆盖等）衡量的是"多少代码被测试执行到"，而非"多少安全相关的行为被验证过"。一个达到 100% MC/DC 覆盖率的测试集，可能完全漏掉系统在非预期外部条件下的行为——例如 ADC 饱和溢出、数据总线被干扰、看门狗超时等。更危险的是，测试用例可能会因为没有针对性地设计而"巧妙绕过"关键的边界条件。正确的做法是基于风险的测试设计——将资源按风险评估的优先级进行分配：对安全关键功能使用最严格的覆盖准则（MC/DC + 形式化验证），对非安全功能使用较宽松的测试策略。

**误区二："保证案例就是一堆文档，对实际系统没有价值"**。高质量的保证案例与"文档堆砌"有天壤之别。文档堆砌的特征是缺乏论证结构，仅仅是测试报告的罗列，隐藏了大量未经验证的前提。有效保证案例的特征是具有清晰的论证结构（GSN 目标->策略->证据形成可追溯的推理链），显式记录所有假设及其合理性论证，在系统变更时能快速评估影响范围。经验表明，精心设计的保证案例在系统演进中可以节省 30%-50% 的重新认证成本。

**误区三："IV&V 是重复浪费资源"**。IV&V 不是简单的"再测一遍"，而是从不同视角、使用不同方法进行的独立评估。开发团队长期沉浸在系统设计中容易形成"认知锚定"，对设计缺陷视而不见。IV&V 团队以全新视角审视需求和测试，能够发现被开发团队忽略的逻辑漏洞。NASA 的经验表明 IV&V 发现的 15%-25% 额外缺陷中，相当一部分属于"如果进入现场将造成灾难性后果"的高危缺陷。

**误区四："测试通过就说明系统满足需求"**。测试用例本身就是对需求的解释，而解释可能偏离用户的实际意图。一个经典问题出现在航天器控制系统上：所有测试用例都通过了，但测试用例中假设的推进器推力曲线与真实推进器的推力曲线在低真空度下有 5% 的偏差——这 5% 的偏差在实际任务中足以导致姿态失稳。因此，需求的 Validation 不能仅靠测试的 Verification 替代。独立的评审、原型验证和确认测试在设计阶段就需要与验证活动并行开展。
