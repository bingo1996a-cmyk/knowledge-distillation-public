# evidence pack schema、release gate 与跨组织评审清单

## 1. 文档用途

这一页是前面多个治理页面的工件层补充。目标不是再讲概念，而是把以下内容模板化：

- evidence pack 应该装什么；
- release gate 在什么条件下通过或驳回；
- 当多个组织共同参与时，评审清单应包含哪些项。

适用场景包括：

- scientific agent；
- space AI；
- 高风险 agentic system。

## 2. evidence pack 是什么

evidence pack 是一组可复核、可追踪、可跨团队传递的证据对象。它应当支持三件事：

1. 说明系统当前为何被允许进入下一阶段；
2. 支持外部或上级评审快速重建关键事实；
3. 在 incident 或质疑出现时，作为 re-verification 的输入。

## 3. 最小 evidence pack schema

建议至少包含以下一级字段：

### A. 系统标识

- system_name
- system_version
- model_version
- deployment_scope
- owner_team
- approver
- creation_time

### B. 边界声明

- intended_use
- excluded_use
- operational_boundary
- autonomy_level
- required_human_oversight

### C. 数据与 provenance

- data_sources
- data_quality_summary
- provenance_statement
- labeling_or_curation_notes
- sensitive_data_handling

### D. 模型与训练

- training_summary
- post_training_summary
- known_limitations
- alignment_or_policy_constraints
- evaluation_snapshot

### E. 验证与评测

- TEVV_summary
- benchmark_results
- scenario_coverage
- red_team_findings
- unresolved_risks

### F. 部署与运行时策略

- runtime_policy_ids
- degradation_playbook_ids
- approval_flow_summary
- monitoring_plan
- incident_contact_chain

### G. 发布结论

- release_recommendation
- decision_rationale
- reviewer_signoff
- expiry_or_revalidation_date

## 4. release gate 的最小问题集

在进入新阶段前，至少回答以下问题：

1. 作用边界是否被清楚定义？
2. 已知高风险动作是否有 policy 覆盖？
3. 关键评测场景是否已覆盖？
4. 是否存在 unresolved blocker？
5. 是否定义了监测与 incident 升级路径？
6. 证据是否足以被外部团队复核？
7. 若环境变化，多久需要 revalidation？

如果上述任一问题无法回答，release gate 就不应视为通过。

## 5. gate 的阶段化设计

### Gate 0：研究探索

重点看：

- 研究目标；
- 数据与方法合法性；
- 初步风险识别。

### Gate 1：原型验证

重点看：

- 基本功能；
- 关键失败模式；
- 最小监测方案；
- 责任链。

### Gate 2：受控试点

重点看：

- 场景覆盖；
- human oversight；
- degradation playbook；
- incident escalation。

### Gate 3：限定范围部署

重点看：

- 运行时策略一致性；
- 证据完整性；
- 外部评审通过；
- 再验证时间表。

### Gate 4：持续运行

重点看：

- drift；
- incident trend；
- 监测有效性；
- 新风险是否触发收紧边界。

## 6. 跨组织评审清单

当系统涉及多个组织、实验室、承包方或政府部门时，建议增加以下检查：

### 6.1 角色与责任

- 谁拥有模型；
- 谁拥有数据；
- 谁负责监测；
- 谁具有叫停权；
- 事故后谁负责取证与通报。

### 6.2 证据互认

- 使用何种 schema；
- 采用什么哈希或版本标识；
- 哪些证据可共享，哪些只能摘要共享；
- 是否有审计访问控制。

### 6.3 边界对齐

- 各组织是否对 intended use 有一致理解；
- 一方允许的动作，另一方是否禁止；
- 是否存在不同的 incident threshold。

### 6.4 更新与失效传播

- 模型或数据更新后，谁通知谁；
- 哪些变更触发联合复评；
- 是否存在证据包的过期机制。

## 7. 常见失败模式

### 7.1 证据存在，但结构混乱

材料很多，但不能快速回答“为什么现在可以发布”。

### 7.2 只交结论，不交原始依据

导致评审人只能相信摘要，无法抽样复核。

### 7.3 跨组织标准不一致

每个团队都有自己的术语、阈值和模板，无法拼成完整 assurance 链。

### 7.4 release gate 形式化

会议开了、表格签了，但高风险项没有真正被讨论。

## 8. 简化模板示例

```yaml
system_name: scientific-agent-x
system_version: 0.9.2
model_version: reasoning-stack-r3
intended_use:
  - controlled scientific workflow execution
excluded_use:
  - unsupervised destructive experiment launch
operational_boundary:
  autonomy_level: advisory_with_approval
  max_concurrent_runs: 4
runtime_policy_ids:
  - RP-101
  - RP-203
monitoring_plan:
  drift_check: daily
  incident_escalation: severity>=2 within 30m
release_recommendation: conditional_approve
revalidation_date: 2026-07-01
```
