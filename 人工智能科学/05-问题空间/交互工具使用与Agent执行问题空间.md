# 工具使用与智能体执行问题空间

## 这页解决什么问题

传统问答系统只需“说”，工具使用型智能体（Agent）必须“做”。它不仅要生成文字，还要决定何时检索、何时调用计算器、何时执行代码、何时操作界面、何时向人类请求批准、何时终止任务。于是问题结构从“输入到输出映射”升级为“带状态、带外部动作、带权限边界的任务执行”。

## 基本思想

这一问题空间的核心不是多会说话，而是能否稳定完成下面的闭环：

1. 理解任务；
2. 发现可用工具；
3. 形成调用参数；
4. 接收外部反馈；
5. 更新内部状态与计划；
6. 在失败时恢复或回滚；
7. 生成可审计的结果说明。

因此，智能体执行问题本质上属于**带工具和环境反馈的序列决策问题**，只是它的动作空间包含 API、数据库、代码执行器、浏览器、文件系统和 GUI 等异构工具。

## 一个直观例子

“总结一篇论文”主要是文本任务；
“检索文献—提取表格—运行代码—生成图—写报告”则是工具使用任务；
“登录系统—点击页面—下载文件—校验结果—提交审批”已经进入 GUI 自动化与权限治理问题。

## 系统骨架

一个最小智能体执行链通常包含：

- 大语言模型（Large Language Model, LLM）：负责计划、解释与参数生成；
- 工具协议：描述可调用能力、输入模式和返回结构；
- 执行器：真正完成搜索、代码、浏览器、数据库或设备操作；
- 记忆层：保存上下文、任务状态、历史操作与外部证据；
- 审计层：记录调用、异常、权限、批准与回滚信息。

## 工程关注点

### 1. 权限与批准流

很多任务不是“能不能做”，而是“是否有权做”“要不要人工确认后再做”。删除文件、发送邮件、提交交易、控制设备等操作都应采用分级授权。

### 2. 工具契约

工具若没有稳定输入输出模式，模型就容易出现参数幻觉、字段缺失、单位错配和异常恢复失败。协议层在这里非常重要。

### 3. 结果验证

真实任务中最危险的不是工具调用失败，而是工具调用“看起来成功、实际上错误”。因此必须引入结果检查、二次确认或外部验证器。

### 4. 长程状态管理

多步任务需要任务图、短期记忆、长期记忆和环境状态同步。否则系统会在数十步后忘记目标、重复操作或污染上下文。

## 常见误区

- 以为“会调用 API”就等于“会做任务”；
- 只做功能演示，不做审计与恢复机制；
- 把权限问题留到上线后再补；
- 不区分文本正确与行动正确。
