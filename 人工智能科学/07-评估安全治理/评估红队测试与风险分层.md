# 评测、红队测试与风险分级

## 定位

这一专题关注的不是“模型有多强”，而是“系统如何被系统性地证明为足够可靠、足够安全、足够可审计”。

它面向的是完整系统，而非单一模型权重。

## 一、概念边界

### 1. 评测不是跑一个 benchmark 就结束

完整评测应覆盖：

- 模型能力；
- 工具调用；
- 长链任务；
- 安全边界；
- 对抗输入；
- 异常恢复；
- 人机协作；
- 审计追溯。

### 2. 红队测试是什么

红队测试（red teaming）是以故障触发、对抗攻击、规避约束、误用路径和极端场景为导向的主动攻击性评估。

它与常规离线评测不同，目标不是估计平均能力，而是发现低概率高损害失效。

### 3. 风险分级的作用

不是所有系统都需要同级别治理。风险分级用于决定：

- 哪些场景需要更严格评审；
- 哪些版本必须人工审批；
- 哪些能力禁止自动开放；
- 哪些日志和 trace 必须保留。

## 二、系统评测框架

建议按五层组织：

1. **单样例层**：单题正确性、拒答准确性、结构化输出质量；
2. **任务层**：工具链、流程链、长任务完成率；
3. **系统层**：时延、成本、吞吐、回滚与观测性；
4. **对抗层**：越权、提示注入、越狱、社会工程学攻击；
5. **治理层**：日志留存、权限控制、责任追溯、发布门槛。

## 三、红队对象

红队测试不应只打模型，还要打：

- prompt/template
- retrieval pipeline
- tool execution
- memory write/read
- approval workflow
- policy layer
- monitoring dashboard
- fallback logic

## 四、风险分级框架

### 一个实用划分

可按潜在损害划分四级：

- **R1 低风险**：错误成本低，可快速回滚；
- **R2 中风险**：错误会影响业务质量或用户决策；
- **R3 高风险**：错误可能造成财务、法律、科研或控制系统显著损失；
- **R4 极高风险**：错误可能带来生命安全、重大财产或系统级外部性后果。

### 每级对应的治理要求

- **R1**：常规离线评测 + 抽样在线监控；
- **R2**：加入对抗样例、回滚机制与更细日志；
- **R3**：必须有人在环（human-in-the-loop）、审批流与版本门禁；
- **R4**：默认不自动执行高影响动作，需多重审批与隔离测试。

## 五、失败模式

### 1. 基准得分高，但系统脆弱

因为评测只覆盖常规分布，不覆盖真实攻击路径。

### 2. 红队只做一次

模型、工具链和用户分布持续变化，一次性红队很快失效。

### 3. 只审模型，不审系统

很多风险源于检索、插件、权限与日志缺陷，而非基础模型本身。

### 4. 风险分级与发布权限脱钩

如果高风险系统与低风险系统采用同样发布流程，风险分级就流于形式。

## 六、评测指标

- task success rate
- refusal precision / recall
- unsafe completion rate
- prompt injection success rate
- tool misuse rate
- harmful recovery failure rate
- audit completeness
- rollback latency
- time-to-detection
- cost per successful task

## 七、研究切口

1. **智能体系统红队自动化**：针对多步工具链构造自动攻击与回归测试。
2. **风险分级与权限策略联动**：把风险等级直接映射为执行权限、审批强度与日志策略。
3. **审计可视化与因果追踪**：研究从 trace 中定位失效根因。
4. **科研与控制场景的专用评测基准**：不能只用通用对话 benchmark 代替专业系统评测。
5. **面向持续更新系统的回归治理**：每次模型、prompt、tool、retrieval 变更都自动触发增量评测。
