# 事件响应、事故复盘与持续监测

## 定位

这篇笔记关注 AI 系统部署后的治理闭环：

- 什么时候判定进入 incident；
- 如何分级、止损、回滚与上报；
- 如何做 postmortem；
- 如何把复盘结果反馈到评测、发布门禁与重新验证。

它承接以下页面：

- `ai-testing-evaluation-verification-and-validation.md`
- `agent-evaluation-observability-and-auditing.md`
- `model-cards-system-cards-and-release-gates.md`

## 一、概念边界

### 1. 持续监测不是线上日志堆积

持续监测（continuous monitoring）至少要覆盖：

- 功能是否继续按设计工作；
- 服务是否稳定；
- 人机交互是否出现偏移；
- 系统是否遭受攻击或滥用；
- 是否触碰合规边界；
- 是否出现大尺度负面影响。

### 2. incident 不是只有安全攻击

AI 系统中的事件至少包括：

- 功能异常；
- 行为漂移；
- 安全事件；
- 数据污染；
- 错误审批或越权执行；
- 高影响错误输出；
- 误触发自动化行动；
- 合规或伦理失配。

### 3. postmortem 不只是"写总结"

真正的 postmortem 需要回答：

- 事件为何发生；
- 事件为何没有更早被发现；
- 哪些控制失效；
- 哪些证据链缺失；
- 哪些重新验证必须补做；
- 是否应该停用、降级或重发版本。

## 二、一个最小治理闭环

可把部署后的治理闭环写成：

发现（detect） -> 分诊（triage） -> 遏制（contain） -> 处置（remediate） -> 恢复（recover） -> 复盘（postmortem） -> 再验证（re-verify） -> 制度修订（governance update）

这条链不应只由安全团队负责，而应连接：

- 模型团队；
- 平台/运维团队；
- 产品或任务负责人；
- 评测负责人；
- 合规/治理负责人。

## 三、监测对象

### 1. 功能监测（functionality monitoring）

关注：

- 关键任务成功率；
- 指标漂移；
- 任务分布变化；
- 长尾失败样例。

### 2. 运行监测（operational monitoring）

关注：

- 延迟；
- 吞吐；
- 调度拥塞；
- 工具调用失败率；
- 依赖组件健康状态；
- 缓存/路由异常。

### 3. 人因监测（human factors monitoring）

关注：

- 用户是否误解系统能力；
- 审批员是否出现自动化偏见；
- 解释是否足够；
- 人工复核是否流于形式。

### 4. 安全监测（security monitoring）

关注：

- prompt injection；
- 越权工具调用；
- 数据外泄；
- 模型绕过 guardrails；
- 对抗样本与数据污染。

### 5. 合规监测（compliance monitoring）

关注：

- 日志保留是否充分；
- 数据处理是否符合规定；
- 模型卡/系统卡是否与真实系统一致；
- 变更是否经过批准。

### 6. 大尺度影响监测（large-scale impacts monitoring）

关注：

- 多用户长期误导；
- 组织流程扭曲；
- 对下游系统的系统性冲击；
- 对高风险场景的外部影响。

## 四、事件分级

建议至少建立四级：

### S0：近失事件（near miss）

未造成实际损害，但已暴露控制缺口。

### S1：局部事件

影响范围有限，可快速回滚，不涉及外部重大影响。

### S2：重大事件

已出现明显任务失败、错误行动、敏感信息泄露或中断，需要跨团队响应。

### S3：严重事件

涉及高风险场景、广泛外部影响、监管/法律后果或人身/财产安全问题。

## 五、事件响应流程

### 1. 触发

触发源可来自：

- 自动告警；
- 审批员上报；
- 用户反馈；
- 红队测试；
- 外部审计；
- 供应链通知。

### 2. 分诊

需要迅速判断：

- 是模型问题、系统问题还是数据问题；
- 是否需要停用；
- 是否需要切到人工模式；
- 是否需要冻结日志与证据。

### 3. 遏制

常见动作：

- 关闭高风险工具；
- 降级到只读模式；
- 切换到旧版本；
- 收紧权限；
- 断开外部依赖；
- 暂停自动执行。

### 4. 处置与恢复

处置不能只修表面症状，还要补：

- 配置；
- 数据；
- 模型；
- 评测集；
- 审批规则；
- 监测阈值。

### 5. 复盘

复盘至少应输出：

- 事件时间线；
- 直接原因；
- 深层原因；
- 控制失效点；
- 影响范围；
- 证据与日志；
- 责任分工；
- 修复项与截止时间。

## 六、日志与证据链

至少应保留：

- 输入与上下文；
- 模型版本；
- 系统配置；
- 工具调用轨迹；
- 审批记录；
- 检索证据；
- 输出与外部动作；
- 人工干预记录；
- 下游系统响应。

对于高风险系统，还应明确：

- 哪些日志可用于取证；
- 哪些日志需脱敏；
- 哪些日志必须不可篡改保存。

## 七、常见失败模式

### 1. 只监控系统性能，不监控行为质量

吞吐正常，不代表输出可靠。

### 2. 只看单点异常，不看长期漂移

部署后很多问题不是瞬时崩溃，而是慢性偏移。

### 3. incident 定义过窄

若只把"外部攻击"当事件，很多由上下文变化、审批失灵、人机交互偏差造成的问题会被漏掉。

### 4. 缺少回滚阈值

没有预定义阈值时，团队容易在"是否停用系统"上犹豫过久。

### 5. postmortem 与重新验证脱节

若复盘后不回流到评测集、门禁规则和发布制度，事件会重复发生。

## 八、关键指标

### 1. 发现指标

- MTTD（mean time to detect）；
- 告警召回率；
- 高影响事件漏报率。

### 2. 响应指标

- MTTA（mean time to acknowledge）；
- MTTC（mean time to contain）；
- MTTR（mean time to recover）。

### 3. 质量指标

- 误报率；
- 近失事件捕获率；
- 回滚后再发率；
- 同类问题复发率。

### 4. 治理指标

- postmortem 完成率；
- CAPA（corrective and preventive actions）关闭率；
- 再验证覆盖率；
- 证据链完备率。

## 九、研究切口

### 1. post-deployment monitoring taxonomy

如何形成跨模型、跨系统、跨行业可复用的部署后监测框架。

### 2. automated triage with human override

如何用模型辅助分诊，同时保留人工 override。

### 3. incident-aware evaluation loop

如何把真实事件自动沉淀到评测集、红队库和发布门禁。

### 4. drift and deceptive behavior detection

如何区分能力退化、上下文漂移、策略伪装与目标漂移。

### 5. monitoring under partial observability

复杂 agent 系统往往只能观察到部分执行轨迹，如何在此条件下进行稳健监测仍是难点。

## 十、结论

AI 系统治理的重点，正在从"上线前一次性评测"转向"部署后持续监测 + 事件响应 + 复盘再验证"。

没有 incident response 与 continuous monitoring，模型卡、系统卡和发布门禁都只能停留在制度文本层。
