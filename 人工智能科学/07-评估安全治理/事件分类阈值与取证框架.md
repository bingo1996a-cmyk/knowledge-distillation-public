# 事件分级、阈值与取证 schema

## 定位

这篇笔记承接 `incident-response-postmortem-and-continuous-monitoring.md`，进一步把 incident handling 从流程层压到工件层。

它关注三个问题：

- 什么样的事件进入什么等级；
- 什么阈值触发升级、冻结、回滚与外部通报；
- 证据链应如何结构化保存，以支撑取证、复盘与再验证。

## 一、概念边界

### 1. incident taxonomy 不是简单严重程度标签

事件分级至少要同时考虑：

- 影响范围；
- 影响对象；
- 可逆性；
- 是否涉及越权、对齐失效、数据污染或物理风险；
- 是否需要停机、回滚、隔离、重验。

### 2. 阈值不是常数，而是制度化触发条件

阈值（threshold）在治理中更接近“决策规则”，例如：

- 错误率超过某值；
- 某类越权调用出现一次即升级；
- 同一类异常在一段时间内重复出现即冻结发布；
- 关键审计字段缺失时，结果不能进入签发链。

### 3. forensic schema 的目的不是存更多日志

取证 schema 的目标是：

- 让事后能够重建事件发生过程；
- 让责任链可验证；
- 让 re-verification 可复现。

## 二、事件分级建议

### 1. 五级结构示例

#### S0：观察项

- 无直接损害；
- 不影响外部输出；
- 用于追踪趋势与早期告警。

#### S1：轻微事件

- 单次、局部、可快速恢复；
- 未越权；
- 未进入关键业务或高风险链。

#### S2：中度事件

- 影响核心指标或用户体验；
- 出现明显偏移、配置异常或监测报警；
- 需要局部回滚、隔离或补充验证。

#### S3：重大事件

- 影响多个组件或关键业务；
- 存在越权执行、明显虚假输出、严重漂移、证据链缺失或高风险领域不当动作；
- 需要强制升级与跨角色响应。

#### S4：严重事件

- 涉及安全、物理、法律、重大合规或组织级声誉风险；
- 需要立即停机、冻结版本、保存证据并开展正式调查。

### 2. 分级维度建议

可按下列维度打分后合成最终等级：

- 影响面；
- 严重程度；
- 持续时间；
- 可恢复性；
- 对抗性；
- 证据链完整性；
- 是否涉及高风险动作。

## 三、升级阈值设计

### 1. 即时阈值

一旦触发立即升级，例如：

- 未授权写操作；
- 模型输出触发被禁止的工具链；
- 高风险动作未经过审批；
- 关键 forensic 字段为空；
- 设备或人员安全边界被突破。

### 2. 累计阈值

在一定窗口内触发，例如：

- 某类 hallucination 比例持续升高；
- 同类 incident 反复出现；
- 监测 drift 指标连续多次越界；
- 关键服务的 rollback 次数异常。

### 3. 组合阈值

多个低级信号同时出现时升级，例如：

- 输出偏移 + 审批记录不一致；
- 工具调用异常 + 缺少 provenance；
- 低置信预测 + 高风险对象 + 弱人审。

## 四、取证 schema 的最小字段

建议至少保存以下字段：

- `incident_id`
- `severity`
- `status`
- `detected_at`
- `reported_at`
- `component_id`
- `model_version`
- `policy_version`
- `tool_call_trace`
- `input_reference`
- `output_reference`
- `approval_trace`
- `operator_identity`
- `environment_snapshot`
- `data_lineage_pointer`
- `evidence_hash`
- `containment_action`
- `rollback_reference`
- `reverification_plan_id`

## 五、证据保全

### 1. 证据对象

需要保全的不只是文本日志，还包括：

- 输入与输出快照；
- 推理轨迹摘要；
- 工具调用 trace；
- 权限校验结果；
- 配置与环境快照；
- 审批记录；
- 外部系统返回值；
- 样品/设备/任务对象状态。

### 2. 保全原则

- 时间戳统一；
- 版本可追踪；
- 不可篡改；
- 权限分层；
- 与数据保护要求兼容。

## 六、从 incident 到 re-verification 的回流

incident 处理不应在 postmortem 处结束，更合理的闭环是：

1. 事件检测；
2. 分级与止损；
3. 证据保全；
4. 根因分析；
5. 修改模型、规则、数据或流程；
6. 重新验证；
7. 更新 release gate 与 monitoring rule；
8. 更新 system card / audit log / training data note。

## 八、常见失败模式

- 事件分级标准与业务风险错位；
- 升级阈值写得过松，导致迟报；
- 升级阈值写得过紧，导致告警疲劳；
- 取证字段不完整，无法重构过程；
- 证据链分散在多个系统中，无法汇总；
- postmortem 没有进入 re-verification，导致同类事件复发。

## 九、评测指标

可用以下指标衡量治理质量：

- 事件检测延迟；
- 错误分级率；
- 取证字段完整率；
- 假阳性与假阴性率；
- containment 平均时长；
- rollback 成功率；
- incident 后重复发生率；
- re-verification 完成率。

## 十、研究切口

1. 如何为 agent 系统设计适合的 severity taxonomy；
2. 如何在隐私、合规和取证之间做日志平衡；
3. 如何把 drift、deception、tool misuse 纳入统一的 incident grammar；
4. 如何让 re-verification 自动回流到 release engineering；
5. 如何把 forensic schema 与 model card、system card、server card 对接。
