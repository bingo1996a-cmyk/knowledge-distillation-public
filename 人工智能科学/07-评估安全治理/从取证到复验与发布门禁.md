# 从 forensics 到 re-verification，再到 release gate

## 位置

这一页承接取证 schema、事故复盘、TEVV 与模型卡/系统卡，讨论高风险 AI 系统在发生异常后，如何把“事故证据”转化为“再验证工件”，再进入新的发布门禁（release gate）。

## 为什么这一页重要

很多系统能监测、能取证、能复盘，但停在“写一份事故报告”。真正困难的是把 incident handling 变成工程闭环：

incident → forensics → root cause → mitigation → re-verification → gated release

## 三类工件

### 1. forensic artifact

包括：

- 关键日志与时间线；
- 输入输出样本；
- 配置快照；
- 模型版本、工具版本、数据版本；
- 环境状态与依赖关系；
- 人工介入记录。

### 2. reverification artifact

事故之后不能只修 bug，还要明确：

- 需要重跑哪些评测；
- 哪些场景必须扩充；
- 哪些阈值要重设；
- 哪些红队用例要升级为回归测试。

### 3. release gate artifact

发布门禁负责回答：

- 现在能不能重新发布；
- 是否只能灰度发布；
- 是否必须增加人工审批；
- 是否要降级或撤回某些能力。

## 典型闭环

1. 事件触发；
2. 冻结关键证据；
3. 根因分析与责任链梳理；
4. 生成修复候选；
5. 构建 re-verification test pack；
6. 更新 model card / system card / risk register；
7. 经过 release gate 决策后再部署。

## release gate 的常见输入

- incident severity
- residual risk estimate
- 覆盖后的测试结果
- 新增红队结果
- 监测策略更新情况
- 人类监督要求是否变化

## 常见错误

1. 修复后没有更新测试集与阈值；
2. 只修单点故障，没有处理同类机制风险；
3. 事故证据与测试用例不连通；
4. 发布门禁只看准确率，不看 residual risk；
5. 没有记录“为什么允许再次发布”。

## 指标

- mean time to containment
- mean time to reverification
- regression coverage gain
- residual risk acceptance consistency
- rollback readiness
- evidence-to-release traceability score
