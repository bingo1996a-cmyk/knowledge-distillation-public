# AI TEVV：测试、评估、验证与确认

## 定位

测试、评估、验证与确认（Testing, Evaluation, Verification and Validation, TEVV）是把人工智能系统从"看起来能用"推进到"可被部署、可被信任、可被审计"的核心过程。

对于高风险系统，TEVV 不应被理解为单次 benchmark 打分，而应是一个贯穿数据、模型、系统、用户场景与部署后监测的生命周期工程。

## 一、概念边界

### 1. Testing

测试（testing）更偏向"看系统在给定条件下表现如何"，常见形式包括：

- 单元测试；
- 基准测试；
- 压力测试；
- 红队测试；
- 场景测试。

### 2. Evaluation

评估（evaluation）更偏向"用什么指标、在哪些任务和场景下衡量能力与风险"。

它回答的是：

- 测什么；
- 如何比较；
- 如何与阈值、基线、人工水平或业务需求对齐。

### 3. Verification

验证（verification）更偏向"系统是否按设计实现"，即：

- 代码与规格是否一致；
- 模块接口是否正确；
- 约束是否被满足；
- 防护机制是否真正生效。

### 4. Validation

确认（validation）更偏向"系统是否适合真实用途"，即：

- 在现实使用场景中是否有效；
- 是否满足任务需求；
- 是否在真实用户与流程中保持可接受风险。

## 二、为什么 AI TEVV 比传统软件更复杂

### 1. 性能依赖数据分布

同一模型在不同输入分布、不同环境或不同用户行为下，表现可能显著变化。

### 2. 系统行为具有概率性和上下文依赖性

特别是生成式 AI 与 agent 系统，输出不是固定映射，而是与提示、工具状态、记忆、外部环境共同决定。

### 3. 风险不仅来自模型，还来自系统耦合

风险可能来自：

- 数据错误；
- 工具接口错误；
- 权限配置错误；
- 人机交互误导；
- 发布流程缺陷。

### 4. 高风险系统需要现实场景验证

离线 benchmark 只能覆盖一部分问题。很多风险要到：

- 长任务链；
- 多用户；
- 多工具；
- 长时间运行；
- 真实组织流程

中才暴露。

## 三、分层 TEVV 框架

建议把 TEVV 分成六层：

### 1. 数据层

检查：

- 数据来源与授权；
- 数据质量；
- 标签质量；
- 覆盖范围；
- 偏差与代表性；
- 数据版本可追踪性。

### 2. 模型层

检查：

- 准确率、召回率、校准；
- 鲁棒性；
- 安全行为；
- 失效模式；
- 对抗脆弱性；
- 不确定性输出。

### 3. 系统层

检查：

- 工具调用正确性；
- 多模块交互；
- fallback 机制；
- 权限边界；
- 缓存、路由、调度；
- 日志完整性。

### 4. 任务层

检查：

- 端到端任务成功率；
- 长链执行稳定性；
- 失败回滚能力；
- 约束与审批触发正确性。

### 5. 用户与组织层

检查：

- 用户是否被误导；
- 输出是否容易被误用；
- 人机职责是否清晰；
- 决策责任链是否完整。

### 6. 现场与生命周期层

检查：

- 真实环境漂移；
- 部署后性能退化；
- 事故上报与复盘；
- 模型更新后的回归测试；
- 退役与封存策略。

## 四、一个最小形式化

可以把部署风险写成能力与环境共同作用的函数：

\[
\mathcal{R} = F(M, D, S, U, E, G)
\]

其中：

- \(M\)：模型；
- \(D\)：数据；
- \(S\)：系统配置；
- \(U\)：用户/组织使用方式；
- \(E\)：环境与场景；
- \(G\)：治理与控制措施。

这意味着 TEVV 不是只评估 \(M\)，而是评估整个 socio-technical system。

## 五、典型 TEVV 流程

### 1. 规格定义

先明确：

- 任务目标；
- 使用边界；
- 不可接受行为；
- 风险等级；
- 发布阈值。

### 2. 离线评估

包括：

- benchmark；
- 数据切片分析；
- 对抗与鲁棒性测试；
- 安全策略测试；
- 校准与不确定性测试。

### 3. 系统集成测试

包括：

- 工具调用；
- API 错误恢复；
- 长链任务；
- 权限与审批逻辑；
- 缓存与版本问题。

### 4. 红队测试

通过恶意、边缘、模糊、跨域与真实工作流诱导系统暴露失败模式。

### 5. 场景化验证

把系统放到近真实业务流程或仿真环境中，检查：

- 用户行为变化；
- 决策质量；
- 错误传播；
- 人机协作效果。

### 6. 上线后监测

包括：

- drift detection；
- incident reporting；
- rollback policy；
- 周期性复评。

## 六、公开治理视角对本分区的启发

近两年公开技术与治理文件中，一个越来越清晰的共识是：AI TEVV 不能只停留在离线准确率。

一个更稳健的框架，应同时覆盖：

- 模型能力；
- guardrail 与红队；
- 真实或准真实场景中的 field testing；
- 与组织流程相连的风险测量；
- 生命周期中的再验证。

因此，本知识库中与 TEVV 相关的页面不能孤立阅读，而应和：

- 审批流；
- 对齐审计；
- 模型卡/系统卡；
- 红队工单；
- 发布门禁

共同构成一条治理主线。

## 七、常见失败模式

### 1. 把 benchmark 当发布门禁

单一 benchmark 分数高，不代表在真实流程中安全可靠。

### 2. 只测模型，不测系统

很多高影响错误来自：

- 工具调用越权；
- 缓存脏数据；
- 记忆污染；
- prompt 注入；
- 审批流失效。

### 3. 只做一次性验证

模型、数据、外部工具和用户行为都会变，因此 TEVV 必须是持续过程。

### 4. 不做切片分析

平均分数掩盖弱群体、弱场景、低频高风险条件下的失败。

### 5. 没有失败后的组织流程

没有 incident class、责任分配、回滚策略和复盘模板，再好的评测也难以落地。

## 八、建议指标

### 1. 能力指标

- 任务成功率；
- 正确率 / 召回率；
- 通过率；
- 完成时间。

### 2. 可靠性指标

- 重复运行一致性；
- 长任务稳定性；
- 故障恢复率；
- 回退触发正确率。

### 3. 安全指标

- 非法输出率；
- 越权动作率；
- guardrail 失效率；
- 红队攻击成功率。

### 4. 不确定性与校准指标

- ECE；
- Brier score；
- selective prediction 曲线；
- abstention 质量。

### 5. 社会技术指标

- 用户误导率；
- 人工复核负担；
- 审计链完整率；
- 事件发现与上报时延。

## 九、高风险领域的特殊要求

在医疗、金融、基础设施、科研自动化等高风险领域，TEVV 还必须额外关注：

- 明确的使用边界；
- 不可接受风险清单；
- 强制审批流；
- 独立审查；
- 数据/模型/供应链溯源；
- 可回滚与人工接管。

## 十一、结论

AI TEVV 的核心价值，不是多一个缩写，而是强迫研究者和工程团队回答五个问题：

1. 系统到底要在什么边界内运行；
2. 哪些行为不可接受；
3. 哪些证据足以支持上线；
4. 出问题时如何发现、回滚和追责；
5. 系统改变后如何重新验证。

如果这些问题没有被结构化回答，那么所谓"安全发布"通常只是表面工作。
