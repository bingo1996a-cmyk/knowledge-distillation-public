## 1. 为什么分词不是小问题

很多初学者把**分词（Tokenization）**看成实现细节，但对大模型来说，它直接影响：

- 训练与推理成本；
- 序列长度；
- 多语言公平性；
- 上下文窗口利用效率；
- 工具调用、代码和数学表达的压缩方式。

因此，本页把分词放到“经济学”视角下讨论：token 如何决定算力、带宽、上下文和语言覆盖。

## 2. token 长度与成本

Transformer 的注意力计算成本通常与序列长度 $n$ 近似呈二次关系。因此，相同文本若被切成更少 token，就能显著降低训练与推理成本。

### 直观例子

- 英文常能被较稳定地压缩成较短 token 序列；
- 中文、日文、黏着语或低资源语言可能在某些分词器下产生更高 token 开销；
- 代码、数学表达和表格也可能出现 token 不均匀问题。

这意味着：同样的上下文窗口，对不同语言与模态的有效容量并不相同。

## 3. BPE、SentencePiece 与字节级建模

### 3.1 BPE

字节对编码（Byte Pair Encoding, BPE）通过频繁子串合并构造词表。优点是简单、压缩率高；缺点是对多语言和稀有形态未必最优。

### 3.2 SentencePiece / Unigram

更灵活，常用于多语言模型。它允许从子词概率视角建模词表。

### 3.3 字节级建模

以字节为基本单位，避免字符集依赖，适合跨语言统一接口，但序列可能更长。

## 4. 上下文利用率

给定窗口长度 $L$，真正关键的不是“名义窗口多大”，而是“有效信息能放进去多少”。

定义一个直观量：

$$
\text{context efficiency} = \frac{\text{有效语义内容}}{\text{消耗的 token 数}}
$$

虽然它不是标准数学量，但能帮助理解：

- 冗长分词会浪费窗口；
- 不合理模板和系统提示会占据大量 token；
- 多轮 agent 流程中，工具返回的冗余文本会迅速吃掉上下文预算。

## 5. 多语言扩展的核心问题

### 5.1 词表偏置

若词表主要由高资源语言主导，低资源语言可能被切得过碎，训练与推理都更吃亏。

### 5.2 训练 token 分配

多语言扩展不仅是“多加语料”，还要考虑：

- 各语言 token 预算；
- 词表公平性；
- 上下文效率差异；
- 不同脚本的归一化与编码。

### 5.3 评价指标

应同时看：

- 困惑度（Perplexity）；
- 多语言基准得分；
- 单 token 信息密度；
- 输入输出成本。

## 6. 分词与 RAG / 工具使用的关系

在检索增强生成（Retrieval-Augmented Generation, RAG）与 agent 系统中，分词决定：

- 文档切块粒度；
- 检索召回的上下文长度；
- 工具参数和返回结果的编码成本；
- 结构化数据是否需要专门序列化策略。

## 7. 与蒸馏、量化、推理优化的关系

- 分词更高效，可减少 FLOPs；
- 更短序列可降低 KV cache 开销；
- 推理优化与 batching 效果会受平均序列长度影响；
- 多语言场景中，token 经济性直接决定服务成本。

## 8. 现实中的权衡

1. 词表太小：序列太长。  
2. 词表太大：嵌入矩阵变大，训练不稳。  
3. 统一分词：跨语言兼容性更强，但未必最优。  
4. 语言专用分词：效率更高，但部署复杂度上升。
