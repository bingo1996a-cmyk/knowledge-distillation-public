## 概念边界

这里讨论的是**推理增强机制**，不是单纯扩大参数规模，也不是把所有问题都交给长链思维。核心问题是：

1. 何时应该多算；
2. 如何生成多个候选推理轨迹；
3. 如何评估、筛选、纠错与回退；
4. 如何在准确率、时延和成本之间做折中。

## 核心组成

### 1. generator

基础模型负责生成候选解、候选中间步骤、候选程序或候选证明草图。

### 2. search policy

搜索策略决定扩展哪些分支。常见形式包括：

- 自洽采样（self-consistency）
- 树搜索（tree search）
- 草稿—验证—修订（draft-verify-revise）
- 程序搜索 / 工具搜索

### 3. verifier

验证器不一定是"真值裁判"，更常见的是局部约束检查器。它可以来自：

- 规则检查
- 单元测试
- 编译器 / 解释器
- 定理证明器或符号求解器
- 辅助判别模型
- 外部数据库或工具调用结果

### 4. controller

控制器负责决定何时继续推理、何时停止、何时切换工具、何时降级为更便宜的路径。

## 典型结构

### 结构一：sample → vote

适合答案空间较窄、验证较弱的问题。优点是实现简单；缺点是代价高且易受模式坍缩影响。

### 结构二：search → verify → prune

适合数学、程序、规划与多步推理问题。关键在于剪枝标准、部分状态表示与计算预算分配。

### 结构三：draft model → target model

先由小模型生成草稿，再由强模型审查、修订或拒绝。其价值在于降低平均推理成本。

### 结构四：reason → execute → observe → repair

适合 agent、scientific workflow、tool-use 与代码执行。执行结果本身成为验证信号。

## adaptive compute 的问题本质

自适应计算不是"永远想得更久"，而是建立一个难度感知机制：

- 简单样本少算；
- 困难样本多算；
- 不确定样本触发验证器或外部工具；
- 高风险样本触发人工审批或保守输出。

## 常见失败模式

1. **伪验证**：验证器只检查表面形式，没有检查语义正确性。
2. **搜索偏置**：模型早期生成的错误分支被过度放大。
3. **奖励黑客**：模型学会迎合 verifier 而不是真正求解。
4. **成本失控**：推理路径过深导致时延和费用不可接受。
5. **错误自信**：在验证器很弱时，多轮推理只会强化错误。

## 评测指标

- 最终任务正确率
- pass@k / solve@budget
- 单样本平均 token / 平均工具调用数
- 端到端时延
- verifier precision / recall
- failure recovery rate
- risk-conditioned refusal quality
