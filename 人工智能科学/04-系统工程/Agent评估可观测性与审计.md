# 智能体评测、可观测性与审计

## 定位

当系统从“单轮回答模型”变为“可检索、可调用工具、可执行多步任务的智能体（agent）”后，传统只看答案文本的评测方法就不够了。真正需要评的是：

- 智能体是否完成任务；
- 它调用了哪些工具；
- 每一步依据什么证据；
- 失败发生在何处；
- 是否可复盘、可追责、可回滚。

因此，智能体工程必须把评测（evaluation）、可观测性（observability）与审计（auditing）作为同一体系来设计。

## 一、为什么“答对了”仍然不够

一个智能体即使最终答案正确，也可能存在以下问题：

- 调用了多余或越权工具；
- 使用了过时或不可靠证据；
- 中间步骤不稳定，偶然成功；
- 成本过高、延迟过长；
- 失败时不可解释，不可复现。

所以，评测对象必须从“输出文本”扩展为“执行轨迹（trajectory）”。

## 二、三层对象

### 1. 结果层

看最终任务是否达成，例如：

- 是否给出正确结论；
- 是否生成正确代码；
- 是否完成表单、搜索、修复、摘要等任务。

### 2. 过程层

看轨迹质量，例如：

- 是否选择了合理工具；
- 是否进行了多余循环；
- 是否正确处理异常；
- 是否在证据不足时中止或请求人工介入。

### 3. 治理层

看系统是否满足上线要求，例如：

- 是否有日志
- 是否可回放
- 是否支持权限控制
- 是否能进行审计抽查
- 是否能对失败样例再评测

## 三、可观测性要观什么

在普通分布式系统里，可观测性通常看日志、指标、追踪；在智能体系统里，还需要额外记录语义级信息。

### 1. 基础工程信号

- 延迟
- 成本
- token 使用量
- 工具耗时
- 错误率
- 超时率
- 重试次数

### 2. 智能体执行信号

- 规划步骤数
- 工具调用序列
- 检索查询与返回证据
- 记忆读写事件
- 人工接管点
- 安全拦截事件

### 3. 质量语义信号

- 是否命中证据
- 是否引用支撑结论
- 是否发生幻觉式工具假报
- 是否出现循环推理
- 是否在不确定时正确拒答

## 四、审计日志的最小字段

建议至少保留以下字段：

1. 用户输入与上下文版本；
2. 模型版本、提示模板版本；
3. 工具定义版本；
4. 调用的工具名称、参数、返回结果；
5. 检索证据 ID、时间戳、来源；
6. 中间状态摘要；
7. 最终输出；
8. 成本、延迟、异常标记；
9. 安全策略触发记录；
10. 人工修正记录。

没有这些字段，后续的失效定位、合规抽查和事故复盘都会很困难。

## 五、评测框架应该怎么分层

### 1. 组件评测

分别测：

- 检索
- reranker
- tool selection
- memory read/write
- planner
- guardrail

### 2. 轨迹评测

测整条执行链是否合理，例如：

- 是否存在无意义回环；
- 是否过早结束；
- 是否忽略关键证据；
- 是否在失败后采取正确补救。

### 3. 任务评测

看端到端任务成功率。

### 4. 线上监测评测

离线过关不等于线上稳定。线上还需要看：

- 新场景失败率
- 分布漂移
- 长尾错误
- 成本突增
- 权限或安全异常

## 六、评分器（grader）如何组织

智能体评测通常要混合三类评分器：

### 1. 规则或代码评分器

适合判断：

- JSON 是否合格
- 代码是否通过测试
- 工具调用是否命中期望接口
- 文件是否正确生成

### 2. 模型评分器

适合判断：

- 回答是否覆盖需求
- 解释是否连贯
- 证据与结论是否基本一致

但它不能直接当作真值，只能当弱监督或预筛工具。

### 3. 人工评分器

对高风险、高价值场景仍不可替代，尤其涉及：

- 医疗
- 法律
- 学术审稿辅助
- 研究决策支持
- 高权限运维

## 七、从可观测到可改进

可观测性的目标不是“存很多日志”，而是支持以下闭环：

1. 发现失败样例；
2. 将失败轨迹切片；
3. 归因到模块或提示；
4. 形成新评测样本；
5. 迭代系统；
6. 回归验证；
7. 再上线。

因此，可观测性本身就是评测集构造器。

## 八、智能体特有失败模式

### 1. 工具幻觉

模型声称已调用工具，但实际上没有成功执行。

### 2. 规划回环

明明已经得到结果，却继续重复搜索、重复读文件或重复推理。

### 3. 证据-结论断裂

检索到证据，但最后结论并不由这些证据支撑。

### 4. 权限穿透

通过工具链意外访问到不应访问的资源。

### 5. 记忆污染

过时偏好、错误事实或旧任务状态在未来被误用。

## 九、与控制与多智能体研究的映射

对控制和多智能体研究者，可以把智能体观测框架类比为一种“数字化实验记录系统”：

- 轨迹 = 执行序列；
- 工具调用 = 控制输入；
- 外部反馈 = 环境观测；
- 评测器 = 性能判据；
- 审计日志 = 实验复现记录。

这意味着，智能体工程中的 observability 与控制系统中的 telemetry、event log、fault tracing 在方法论上是同构的。

## 十、资源受限条件下的最小可行方案

若资源有限，不必一开始就上全栈平台。最小方案可以是：

1. 统一记录 trace id；
2. 保存每次工具调用与返回值；
3. 保存检索证据 ID；
4. 构造 50-200 条高价值任务集；
5. 对失败样例做人工标注；
6. 建立周级回归评测。

这已经足以淘汰大量“看起来能跑、实际上不可维护”的智能体原型。

## 十一、博士研究切口

1. 面向 agent workflow 的轨迹级评测方法。
2. 证据支撑率与任务成功率联合度量。
3. 面向高风险智能体的审计日志压缩与回放。
4. 结合因果归因的失败分析方法。
5. 面向多智能体协同工作流的分布式 observability。
