## 1. 为什么需要这一页

前面的页面已经讨论了 KV cache、推测解码、连续批处理，但生产级大模型服务还需要进一步回答三个问题：

1. 请求谁先服务；
2. cache 放在哪，如何回收；
3. 多个租户共用一套服务时，如何兼顾延迟、吞吐与隔离。

## 2. Serving 调度器的基本职责

一个推理调度器至少负责：

- 请求排队；
- 动态批处理；
- 资源分配；
- 优先级管理；
- 中断与恢复；
- 监控与限流。

## 3. 常见调度策略

### 3.1 FIFO

先进先出。简单，但可能让短请求被长请求拖慢。

### 3.2 Shortest-Remaining-Processing-Time 类策略

优点：降低平均延迟。  
缺点：长请求可能饥饿。

### 3.3 优先级调度

适合将交互式请求、后台批处理、工具调用区分开来，但要防止低优先级请求长期得不到服务。

### 3.4 连续批处理（Continuous Batching）

不是等待整批再算，而是在解码过程中不断插入新请求，提高 GPU 利用率。

## 4. KV cache 布局问题

KV cache 本质上是解码阶段最重要的状态资产之一。关键问题包括：

- 按序列分配还是按页块分配；
- 何时回收；
- 是否跨请求共享前缀；
- 是否跨设备迁移。

### 常见设计考虑

1. **页式缓存**：便于碎片管理；  
2. **前缀共享**：适合相同 system prompt；  
3. **冷热分层**：热 cache 驻留 GPU，冷 cache 回落主存；  
4. **回收策略**：LRU、优先级淘汰或租户配额。

## 5. 多租户推理

多租户（Multi-Tenant）意味着不同用户、模型头、adapter 或工具流共享一套服务基础设施。挑战包括：

- 资源争抢；
- 隔离性；
- 数据与 cache 泄漏风险；
- SLA 不同；
- 配置与模型头切换成本。

### 常见解决思路

- 租户级队列；
- 配额与限流；
- adapter 动态装载；
- 按租户隔离 cache 或做命名空间划分；
- 关键租户预留算力。

## 6. 调度与成本的关系

调度器并不只是“排队器”，它直接影响：

- 首 token 延迟；
- 每 token 延迟；
- 吞吐；
- GPU 利用率；
- OOM 风险；
- 租户公平性。

## 7. 与推测解码、KV cache 的关系

- 推测解码会改变 token 生成模式，对调度与 cache 占用提出新要求；
- 更高的前缀共享度，会改变 cache placement 的最优策略；
- 连续批处理与 cache paging 往往要联合设计。

## 8. 监控指标

建议至少监控：

- queue time；
- first-token latency；
- per-token latency；
- cache hit/miss；
- GPU memory fragmentation；
- tenant fairness；
- abort / retry / overload 率。
