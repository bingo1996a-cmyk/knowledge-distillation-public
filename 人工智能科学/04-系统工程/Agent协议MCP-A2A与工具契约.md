# 智能体协议：模型上下文协议（MCP）、智能体到智能体协议（A2A）与工具契约

## 这页解决什么问题

当智能体系统从“单个模型调用少量本地工具”发展到“多个模型、多个服务、多个智能体跨系统协作”时，真正的瓶颈不再只是提示词，而是**协议**。协议决定：
- 工具如何被描述与发现；
- 输入输出模式如何标准化；
- 智能体如何互相声明能力；
- 外部上下文、工具和身份信息怎样安全传递。

没有协议层，系统只能靠临时脚本和私有约定勉强工作；一旦规模上来，就会出现接口漂移、能力不可发现、权限不可审计、跨团队无法互操作等问题。

## 基本思想

可以把协议层理解为“智能体时代的接口说明书 + 服务目录 + 交互规则”。它至少应覆盖三类对象：

1. **工具契约（tool contracts）**：工具叫什么、接收什么参数、返回什么结构、失败时怎样报错；
2. **上下文协议**：模型怎样读取外部资源、文档、提示模板、会话状态和能力描述；
3. **智能体互操作协议**：一个智能体怎样向另一个智能体声明能力、发起任务、交换状态与结果。

## 为什么协议层现在变得重要

工具调用和智能体编排已经从“技巧”逐渐转向“基础设施”。MCP 作为开放协议，强调模型应用与外部数据源、工具之间的标准化连接；A2A 则面向智能体间的发现、通信和协作。官方文档都已把这两类问题从产品特性上升为协议问题。citeturn658575search0turn658575search1turn658575search9

## 工具契约的最小要求

一个合格的工具契约通常至少包含：

- 工具名称与版本；
- 输入参数模式；
- 输出结构模式；
- 失败码与异常语义；
- 幂等性、超时、重试与副作用说明；
- 权限等级与审计要求。

这不是形式主义。工具若没有清晰契约，模型很容易在参数名、单位、默认值、枚举范围、分页规则等细节上产生错误。

## MCP 的作用边界

MCP 的核心价值是把“模型如何连接上下文和工具”标准化。官方规范明确它是开放协议，并以 TypeScript schema / JSON schema 形式定义消息与结构。citeturn658575search0turn658575search4turn658575search12

面向工程时，MCP 更适合作为：
- 工具暴露与发现的统一层；
- 资源与提示模板的结构化描述层；
- 模型应用与外部系统之间的稳态接口。

它不能自动解决权限、商业流程、身份委托和跨组织治理，但为这些问题提供了基础接口层。

## A2A 的作用边界

A2A 的重点不是“一个模型调用一个工具”，而是“一个智能体怎样和另一个智能体发现彼此、声明能力、交换任务与结果”。Google 的官方介绍把 A2A 定位为智能体间安全通信与跨企业系统协作的协议，并强调 Agent Card 作为能力声明机制。citeturn658575search1turn658575search5turn658575search9

它更适合：
- 多智能体任务分工；
- 跨系统、跨团队的能力编排；
- 把专用智能体接入统一工作流。

## MCP 与 A2A 的关系

两者不是替代关系，而是层次不同：

- MCP 更像“模型—工具/上下文”的接口层；
- A2A 更像“智能体—智能体”的互操作层。

一个复杂系统完全可能同时采用两者：智能体内部通过 MCP 接工具，对外通过 A2A 与其他智能体协作。

## 工程关注点

### 1. 契约稳定性

接口字段一旦频繁变化，智能体工作流会迅速失稳。协议层必须有版本化和兼容性规则。

### 2. 可发现性

工具与智能体不能只存在于文档里，必须可被程序检索、校验和测试。

### 3. 权限与审计

协议描述能力，不等于自动授权。高风险动作必须与认证、批准流和审计日志联动。

### 4. 失败语义

如果协议只规定成功返回，不规定失败模式，智能体就很难执行恢复、重试或回滚。

## 常见误区

- 把协议看成“格式转换”；
- 只做 happy path，不定义异常路径；
- 以为统一 JSON 就等于有协议；
- 忽视版本治理和能力声明。
